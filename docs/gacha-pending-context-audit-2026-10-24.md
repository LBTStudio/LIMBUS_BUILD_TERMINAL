# 抽選確認中の条件変更と履歴メタデータの監査（2026-10-24）

## 発見

ショップの抽選確認では `pending` に決定済みの出目（`out`）だけを保持していました。確認画面を開いたあとも、抽出ルート・パック・支払い方法・チケット種別・回数の操作は有効で、確定処理は古い `out` を使用する一方、`drawLogEntry` の `route` と `times` は最新レンダーの状態から記録していました。

この順序で操作すると、実際にはE.G.Oを1回抽選したのに、記録側は後から選び直した人格ルートや回数を記録するなど、抽選ログのメタデータと封緘バッチ／結果が食い違い得ます。支払いのトランザクション本体がただちに二重実行される問題ではありませんが、後日の履歴確認や監査の信頼性を損ないます。既存の回帰テストには、この確認中の設定変更順序を検査するケースがありませんでした。

## 修正

- 出目を確定待ちにした瞬間のルート・支払いモード・パック・チケット種別・回数を、pendingリクエストに一緒に保存する。
- 確定時の抽選ログは、現在のフォーム状態ではなく、保存済みのリクエスト条件を参照する。
- 確認中は抽選条件と再申込ボタンを無効化し、条件を変える場合は「まだ引かない」で確認を解除してから操作させる。
- 画面に条件固定の説明を追加し、挙動を利用者に明示する。

## 回帰テスト

`tests/gacha-pending-context.test.mjs` で、申込時点の条件保存、確定ログへのスナップショット利用、確認中の設定ロックとキャンセル導線を検査する。

## 制約

これは抽選ログのルート／回数の整合性を保つUI状態管理の修正であり、抽選結果をseedから再計算して公平性を暗号学的に証明する仕組みを追加するものではない。
