# LBT Share Fabric — 中央停止を避ける長文共有方針

調査日: 2026-08-17  
対象: LIMBUS BUILD TERMINAL の、1万文字級のオリジナル人格・アイテムを含む共有

## 結論

LBTは、長文共有用に**LBT運営者が所有する中央API、データベース、無料枠を置かない**。代わりに、発行者のブラウザが独立した匿名文書公開サービスへ同時に投稿する **LBT Share Fabric** を採用する。初期の二系統は **Rentry** と **Telegraph** である。

この方針では、LBTの中央無料枠、保存容量、日次リクエスト上限が尽きたために全利用者の新規共有が停止することはない。発行処理・保存負荷・サービスごとの投稿制限は、LBTの外部に分散する。請求情報、支払いアカウント、LBT管理サーバーは不要であり、発行者・閲覧者はログイン、登録、CAPTCHA、手動保存、期限管理を求められない。

> **到達できない保証**: 無料かつ無契約の第三者サービスを用いる以上、「世界中のすべての投稿先が永遠に停止せず、無制限に匿名投稿を受け付ける」ことは保証できない。この主張が可能になるのは、利用者自身の常時運用ストレージ、又は支払い・契約を伴う基盤だけである。LBTが保証する範囲は、**LBT固有の中央無料枠が発行停止点にならないこと**と、独立サービスへの同時発行により単独停止を共有停止へ直結させないことである。

## 採用アーキテクチャ

| 層 | 目的 | 方式 | 中央LBT枠 | 閲覧時の体験 |
| --- | --- | --- | --- | --- |
| 0 | 小〜中サイズの最速共有 | GitHub Pagesのfragmentへ可逆圧縮状態を格納 | 不要 | LBTの完全ビューアを即時復元する |
| 1 | 5,000文字以下のURL短縮 | is.gdで層0 URLを301短縮 | 不要 | LBTの完全ビューアを即時復元する |
| 2 | 1万文字級以上の完全保持 | 発行者ブラウザからRentryとTelegraphへ並列投稿 | 不要 | 人が読みやすい長文シートとDiscordカードを返す |
| 3 | 外部文書からLBTへ再読込 | `share.html?source=<provider>&id=<id>` が公開本文をCORS取得し、埋込トークンを復元 | 不要 | LBTの完全ビューアで編集・出力できる |

長文時は、発行操作の内部で次の処理を一度に行う。LBTは可逆圧縮済みトークンを生成し、本文に「読みやすいシート」と「機械読取専用のLBTペイロード」を入れる。RentryにはMarkdownとメタデータ、Telegraphには安全なDOMノード列として同じ内容を送る。投稿は`Promise.allSettled()`で並列化し、片方が失敗しても成功側のURLを直ちに返す。両方成功した場合はRentryを主URL、Telegraphを冗長URLとして表示する。

## 要件への適合性

| 要件 | 対応 | 重要な限界 |
| --- | --- | --- |
| 発行者・閲覧者のログイン等を不要にする | 両サービスの匿名APIをブラウザから直接呼ぶ | 送信元IP単位の混雑・サービス側の不正利用対策は存在し得る |
| LBT運営者への請求をゼロにする | LBTの保存API、クラウドDB、決済設定を使わない | 外部サービスの利用規約に従う必要がある |
| LBT中央無料枠による新規発行停止を除く | LBTは保存も中継もせず、二つの外部サービスへ直接投稿する | 二サービスの同時障害・同時拒否は残る |
| 1万文字級データを完全に保持する | 圧縮トークンを全文書へ埋め込み、復元時はトークンを唯一の正本とする | TelegraphはDOM本文64 KBまで。超過時はRentryのみを主とする |
| Discord本文2,000文字以内 | 公開先が返す短いURLだけをコピーする | URLのカード表示はDiscordのキャッシュ方針に従う |
| 最低1〜3日、理想は恒久 | Rentryは規約違反等を除き永久保存を案内し、二系統へ複製する | 第三者サービスの永続性をLBTは保証しない |
| Discordで人格名を識別する | Rentryの`SHARE_TITLE`、Telegraphの`title`へ人格名を設定する | 画像カードを任意指定できない公開先がある |

## 実測根拠

Rentryは匿名発行、200,000文字の本文上限、永久保持の方針、公開API、二重サーバー複製と日次バックアップを説明している。[1] 11,195文字かつ日本語引用符・スラッシュ・記号を含む検証文書は、短いRentry URLとして発行・HTTP 200取得できた。Rentry raw本文はGitHub PagesをOriginとする要求に`Access-Control-Allow-Origin: *`を返したため、LBT側の再読込に利用できる。

Telegraphは匿名アカウント作成と公開ページ作成APIを提供し、ページ本文を最大64 KBのDOMノード列として受け付ける。[2] 11,000文字級の検証文書を短いURLとして発行し、HTTP 200で取得できた。`getPage?return_content=true`もCORS許可を返す。ただし、Telegraphが外部iframeを独自の`/embed/`表現へ置換する実測があるため、LBTの完全HTMLをiframeとして封入する用途には使わない。

小さい共有については、現在のGitHub Pages自己完結方式を維持する。これは発行ごとの外部通信を必要とせず、URLのfragmentに保持された可逆データをLBTで復元する。長文用の層2はこの経路を置き換えず、URL長の物理的限界を超えた場合だけ自動的に追加する。

## 実装契約

| 項目 | 契約 |
| --- | --- |
| 正本 | `encodeState` が生成する可逆トークン。表示用Markdown/DOMは補助表現であり、復元の正本ではない。 |
| 外部文書 | 人格名、同期、ステータス、スキル、E.G.O、所持品、MEMO等の読みやすいシートと、目視を妨げない機械読取ペイロードを含める。 |
| 復元 | `share.html` は外部本文を取得し、厳格なプレフィックス・長さ・デコード検証後に既存の`decodeToken`へ渡す。任意HTMLを実行しない。 |
| 発行 | 標準フォーム送信のみを使い、ブラウザのCORS許可範囲で直接POSTする。アクセス・編集トークンはメモリ上だけで使い、URL・保存データ・画面ログへ残さない。 |
| フォールバック | RentryとTelegraphを並列試行する。Rentryが成功すれば主URL、Telegraphのみ成功ならそのURLを主URLにする。両方失敗した場合だけ、失敗理由と再試行を示す。 |
| 保護 | 原則として公開データを扱う。アクセストークン、編集コード、または個人情報を共有データへ含めない。 |

## 実装時の代償

公開先のシートはLBTの既存CSS・レイアウトを完全には再現しない。代わりに、Discordに貼った短いURLは人格名が分かる公開カードと読みやすいテキストシートを返し、「LBTで開く」操作では既存の完全ビューアへ戻る。この分離により、見た目の完全一致よりも停止耐性、請求ゼロ、長文完全保持、Discord互換性を優先する。

また、RentryとTelegraphは第三者の公開サービスである。規約違反、不正利用防止、サービス停止、ネットワーク障害による投稿失敗をLBTが回避・補償することはできない。実装は失敗を隠さず、成功した投稿先を明示し、二系統のうち一方が失敗しても共有を完了する。将来、同じ契約を満たす追加の匿名公開先が実測確認できた場合は、第3の並列配送先として追加できる。
