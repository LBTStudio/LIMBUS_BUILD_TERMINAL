# /goal — 原典の段落構造をCCFOLIA出力まで保つ

## 背景（利用者から報告された事象）

特異人格「N社握らんとする者」戦術4「自滅的浄化」の3番目のダイスで、
`敵討伐時` から始まる本文が改行されず、直前の `使用時効果` に連続して挿入される。

報告は一例だが、利用者の指摘どおり問題は個別の人格ではない。

> これは一例のみを取り上げたもので、これだけが問題ではなく、
> データベースあるいはそのデータベースの信ぴょう性検査、
> そして実際に抽出して反映する段階のプロセスなどの監査が必要です

したがって監査対象は次の三段階すべてとする。

1. **データベース** — `data/db.json` が原典PDFの段落構造を保持しているか
2. **信ぴょう性検査** — 段落構造の欠落を機械的に検出できるか
3. **抽出・反映プロセス** — DBが正しい場合、出力生成が段落構造を壊していないか

## 先行作業との関係（なぜ「完了済み」が再発したのか）

`docs/data-provenance-goal.md` は同種の報告に対する先行作業で、完了条件を
「両監査が0件」「全テスト成功」として達成を宣言している。
今回の事象が起きている状態で、その完了条件は現在も**すべて満たされている**。

```
node tools/provenance/audit-output-lossless.mjs  → 検出: 0件
node tools/provenance/audit-db-text.mjs          → 要修正: 0件（不在0 + 切断0）
```

つまり先行作業の欠陥は個別の見落としではなく、**監査の設計**にある。
本作業は先行作業を置き換えるものではなく、その監査が
「検出できない領域」を三点で特定し、塞ぐことを目標とする。

### 欠陥A — 段階3の監査が実出力を見ていない

`audit-output-lossless.mjs` は `splitEffectLinesPlain()` を直接呼び、
その戻り値だけを検査する。しかし利用者が受け取るのは
`buildPalette()` / `buildMemo()` / `buildCcfoliaJSON()` / 共有シートの出力である。

ダイス効果 `d.effect` は `splitEffectLinesPlain()` を**一度も通らない**。
`sanitizeInline()` が `\r\n|\r|\n` を空白へ置換した後、
`${roll}：${showDeff}` として直接連結される（`js/generator.js`）。

監査が通る経路と、出力が通る経路が別である。
段落分割器をいくら検査しても、分割器を使わない経路の欠陥は永久に検出されない。
これが報告事象の直接原因である。

### 欠陥B — 段階1の照合が段落構造を見ていない

`db-provenance.mjs` の `canon()` は比較前に空白と改行をすべて除去する。

```js
const NOISE_RE = /[\s\u3000。、，,．.・：:；;／/]/g;
```

改行の有無は比較に影響しない。よって
「原典が2段落で書いている本文を、DBが1段落へ連結している」型の破損は
定義上検出できない。`canon()` は文字の混入・欠落には有効だが、
段落構造については無力である。

### 欠陥C — 「0件」が監査の健全性を意味していない

段階3の監査は、検査対象（分割器）と出力経路が乖離しているため、
出力側がどう壊れていても0件を返す。
先行作業の「再発防止の要点」は分割器への変更に対して非空虚性を確認しているが、
出力経路への変更に対しては確認していない。

## 出典（Single Source of Truth）

- `sources/新リンバスTRPG.pdf`（基本ルールブック、378頁）
- `sources/新リンバスTRPG サプリメント 『アンロックド・シンク』.pdf`（177頁）

本作業でPDF本体をリポジトリへ格納した。以後コーパスの再生成は
リポジトリ内のみで再現できる（先行作業はPDFが手元にある場合に限られていた）。

## 段落境界の判定基準（本作業の技術的中核）

PDFから抽出した行は、次の二つが区別できない。

- **折り返し** — 一つの段落が組版上の桁数で折り返されただけ
- **段落境界** — 原典が意図して改行した位置

両者を推測ではなく組版情報で判定する。PyMuPDFの行bboxを使い、
**行が段（セル）の右端まで到達しているか**を見る。

| 行 | x1 | 段の右端 | 余白 | 判定 |
|---|---|---|---|---|
| `自分に狂信があるならダメージ量+5。対象が機械融和生命体なら追` | 252.19 | 252.19 | 0.0 | 折り返し |
| `30-6d5：的中時、対象の出血が5以上なら火傷7を付与。` | 224.64 | 252.19 | 27.5 | **段落境界** |

次の文字が入る余白（1文字分）を残して行が終わっていれば、
そこで改行されたのは組版の都合ではない。原典が改行した位置である。

紙面206では `火傷7を付与。` の行が右端より27.5pt（4文字分以上）手前で終わり、
続く `敵討伐時、次のRに打撃威力増加1を得る` は字下げ位置も異なる（x0=98.45 対 71.42）。
原典はここで改行している。DBもこの改行を保持している。
**壊しているのは出力生成である。**

## 目標（Goal）

### G1. 出力生成が原典の段落構造を保つ

DBの本文に含まれる改行が、CCFOLIA出力の全経路で改行として現れる。
対象は次の四経路すべてとする。

| 経路 | 改行の表現 |
|---|---|
| チャットパレット | `\n`（CCOLIAの文字列改行、1コマンド内に保持） |
| メモ | 実改行 |
| CCFOLIA JSON | `\n` |
| 共有シート | `<br>` |

ダイス効果を含め、自由文を出力する経路はすべて段落分割器を通す。
分割器を通らない経路を残さない。

### G2. 段階3の監査が実出力を対象とする

監査は `splitEffectLinesPlain()` ではなく、
`buildPalette()` / `buildMemo()` / `buildCcfoliaJSON()` / `buildShareSheetHTML()`
の戻り値を検査する。全人格・全E.G.Oを装備した状態で実行する。

### G3. 段階1の照合が段落構造を対象とする

原典PDFの組版情報から段落境界を判定したコーパスを作り、
DBの改行位置が原典と一致することを照合する。
`canon()` による文字照合（先行作業のG2）は維持し、段落照合を追加する。

### G4. 監査の非空虚性を機械的に示す

各監査に対し「検出すべき破損を注入すると必ず検出する」ことを
テストとして常時実行する。人手による一度の確認では、
経路が増えたときに空虚化したことを検出できない。

これは先行作業が「再発防止の要点」として人手で確認した手順を、
テストへ昇格させるものである。

## 非目標

- TRPGのルール解釈・裁定の変更
- PDFに書かれていない独自バランス調整
- 保存データ形式（`lbt_v46_state` / `schemaVersion: 2`）の変更
- 原典の折り返し位置の再現（折り返しは組版の都合であり意味を持たない）

## 基本方針（Plan）

| 手順 | 内容 | 成果物 |
|---|---|---|
| P1 | 原典PDF2冊をリポジトリへ格納する | `sources/` |
| P2 | 組版情報から段落境界を判定するコーパス抽出器を作る | `tools/provenance/extract_pdf_corpus.py` |
| P3 | 出力経路の自由文をすべて段落分割器へ通す | `js/generator.js` |
| P4 | 段階3の監査を実出力に対して行うよう作り直す | `tools/provenance/audit-output-paragraphs.mjs` |

| P7 | 破損の型ごとの回帰テストを追加し全テストを通す | `tests/output-paragraphs.test.mjs` 他 |

### P3 の設計方針

ダイス効果を段落分割器へ通すと、段落は複数行になりうる。
出力の各経路は、その経路の改行表現で段落を連結する。

パレットでは、ダイス行は `{ロール}：{効果}` の形を保つ必要がある。
効果が複数段落になる場合、2段落目以降は先頭に `\n` を置いて
同じコマンド内へ収める。ロール表記が段落ごとに重複してはならない。

### P5 の判断基準

段落照合で差分が出た場合、原典の紙面を根拠に判断する。

- 原典が改行し、DBが連結している → DBへ改行を補う
- 原典が改行しておらず、DBが改行している → 原典に合わせる
- 原典の組版が判読できない（段組みの境界・改ページ等） → 例外登録

段落の判定は組版情報に基づくため、紙面の折り返しが
段の右端ちょうどで終わる場合は判定できない。この場合は差分として報告せず、
判定不能として別区分にする（偽陽性を出さない）。

### 修正の内容

**段階3（出力生成）**

- ダイス効果へ `sanitizeInline()` を適用していた4箇所を、段落分割器を通す
  `formatDiceEffectDisplay()` へ置き換えた。パレット・JSON・同化スキル・
  E.G.O（覚醒/侵蝕）のすべてを含む。段落の連結は経路ごとの改行表現に任せ、
  ロール表記は先頭段落にのみ付けて重複を避けた。
- メモはDBの改行でのみ行を分けていたため、原典が改段していてもDB側が1行で持つ
  本文はパレットと食い違っていた。`pushMemoEffect()` で段落判定を分割器へ集約した。
- 段落分割器の `ROUND_STAGE_MARKER` が `\d+R` の直後に非数字が続くだけで分割し、
  持続表記まで切っていた（`怠惰保護2を` / `3Rの間付与する`）。
  原典の分布（段落の先頭に立つ47件中44件が `\d+R：`）を根拠に、
  区切り記号を伴う場合だけを見出しとした。14件の誤分割が解消した。

**段階1（DB本文）63件**

- 原典が改段している位置で改行が落ちていた62件を修復した。
- 原典が一文で書いている位置に改行が入っていた1件を修復した。
- いずれも文字は変えず、改行の位置だけを原典へ揃えた。
  修復は `repairs.json` へ出典・理由つきで記録し、`before` が現在値と
  一致しなければ適用を中止する既存の仕組みに乗せた。

**照合基盤**

- 組版情報から段落境界を復元するコーパスを追加した
  （`data/provenance/*.paragraphs.txt`）。
- 原典PDF2冊を `sources/` へ格納し、コーパス再生成をリポジトリ内で完結させた。

### 再発防止の要点

監査が空虚でないことを、次の五点でテストとして常時確認している
（`tests/audit-non-vacuity.test.mjs`）。

- 4つの出力経路それぞれについて、改行を空白へ潰すと段階3の監査が検出すること
- 壊していない経路は指摘されないこと（常に何か検出するだけの試験にしない）
- DBの改行を落とすと段階1の段落照合が検出すること
- 原典に無い改行を入れると段階1の段落照合が検出すること
- 監査が検査対象を実際に集めていること（対象0件でも「検出0件」と表示されるため）

先行作業の欠陥は、監査対象と出力経路の乖離が「0件」という表示の裏で
放置されたことにある。経路を追加したときに監査が追随しているかは、
人手の確認では保証できない。非空虚性をテストへ組み込むことで、
この乖離自体を検出対象とした。
