# /goal — 出典照合による本文完全性の保証

## 背景（利用者から報告された事象）

CCFOLIA用の出力で、特異人格「N社握る者」のスキル本文が途中で寸断され、
また `敵討伐時` のような発動タイミング見出しが独立した行として改行されない、
という報告を受けた。

報告は一例だが、問題の本質は個別の人格ではない。
寸断がどこで起きているのか、どの段階の責任なのかを切り分ける仕組みが存在せず、
「同じ型の破損」が別の人格で再発しても検出できない状態そのものが欠陥である。

したがって、個別修正ではなく、次の三段階すべてを監査対象とする。

1. **データベース** — `data/db.json` の本文が原典PDFと一致しているか
2. **信ぴょう性検査** — 一致していないことを機械的に検出できるか
3. **抽出・反映プロセス** — DBが正しい場合、出力生成（整形・改行・分割）が本文を壊していないか

## 出典（Single Source of Truth）

- `新リンバスTRPG.pdf`（基本ルールブック、378頁）
- `新リンバスTRPG サプリメント 『アンロックド・シンク』.pdf`（177頁）

この二つのPDFが唯一の原典である。LBTのDBはこのPDFの転記物であり、
PDFに存在しない本文はDBに存在してはならない。

## 調査で確定した事実

### 段階3（出力生成）の欠陥 — 利用者報告の直接原因

`js/generator.js` の段落分割器 `splitEffectLinesPlain` / `splitEffectLines` は、
ラウンド進行表記を段落境界として扱うため `\d+R` の直前で分割する。
この判定に文脈の考慮がないため、次の二つを本文の途中で切断していた。

| 入力 | 誤った出力 |
|---|---|
| `[1R] 数値2ごとにダメージ量が1増加` | `[` / `1R] 数値2ごとに…` |
| `攻撃的中時、視線1を付与（1Rに2回）` | `攻撃的中時、視線1を付与（` / `1Rに2回）` |

`[1R]` は「1ラウンド持続」を表す状態表記、`（1Rに2回）` は発動回数の制限であり、
どちらもラウンド進行の段落見出しではない。DB全体で **59件** の本文が影響を受けていた。
「N社握る者」の固有バフ「狂信」「注視」もこれに該当し、
チャットパレットへ `効果：▶︎[` と出力され、直後に本文が分断されていた。

### 段階1（DB本文）の欠陥

PDF二冊を全文抽出し、DBの全本文（人格・E.G.O・固有バフ・ダイス効果）が
原典に実在するか照合した結果、**PDFのどこにも存在しない本文が68件**あった。
PDFの二段組みレイアウトと改ページが原因の、次の型の破損である。

- **隣接列の断片が末尾へ流入** — 例: `一方攻撃時：縛り付く鉄線3を付与` + `ダメージを与える`
- **本文が途中で終端** — 例: `使用時：対象の束縛が3以上ならスキル威力+2` + ` 動を10消費`
- **用語集の定義が部分的にしか転記されていない** — 例: 固有バフ `あなたの盾` が
  PDF紙面306の定義から「R終了時、数値が半減（最大10）」を落としている

### 段階2（信ぴょう性検査）の欠陥

既存の `tests/db-text-integrity.test.mjs` と `js/DataQuality.js` は、
末尾が助詞で終わるなど「破損の形」を推測するヒューリスティックしか持たない。
原典と突き合わせていないため、上記68件をすべて見逃していた。
また過去に修正した箇所を個別に固定するテストが増える一方で、
同じ型の再発を防げていない。

## 目標（Goal）

次の四点を満たす状態にする。

### G1. 出力生成が本文を壊さない
DBの本文をCCFOLIA出力（チャットパレット・メモ・JSON・共有シート）へ通したとき、
句読点・空白の正規化を除き、文字が欠落・分断・重複しないことを保証する。
段落分割は意味のある発動タイミング見出しの位置でのみ行い、
`[1R]` のような状態表記や `（1Rに2回）` のような回数制限では分割しない。

### G2. DB本文が原典PDFに実在する
すべての本文断片が、対応するPDF紙面に（句読点・空白の差を許容して）実在する。
実在しない本文はPDFを根拠に修正するか、根拠を明示して例外登録する。

### G3. 信ぴょう性検査が機械化・再現可能である
PDFからの全文抽出とDBとの照合を、コマンド一つで再実行できる監査ツールを持つ。
監査結果は人格名・項目パスつきで出力され、差分の所在が特定できる。

### G4. 同じ型の再発をテストで止める
G1・G2をテストスイートに組み込み、
「破損の型」に対する回帰テストとして常時実行する。
個別の人格を狙った固定テストは、型のテストを補うものとして残す。

## 非目標

- TRPGのルール解釈・裁定の変更（LBTは参照情報を整えるツールであり、裁定はしない）
- PDFに書かれていない独自バランス調整
- 既存の保存データ形式（`lbt_v46_state` / `schemaVersion: 2`）の変更

## 基本方針（Plan）

| 手順 | 内容 | 成果物 |
|---|---|---|
| P1 | PDF二冊を全文抽出し、人格名でPDF紙面ブロックへ索引付けする監査ツールを作る | `tools/provenance/`（README・抽出・監査・修正の各スクリプト） |
| P2 | 段落分割器を、状態表記・回数制限を保護するよう修正する | `js/generator.js` |
| P3 | 監査で検出したDB本文を、PDF紙面を根拠に修正する | `data/db.json` |
| P4 | 出力の無損失性（G1）と出典実在性（G2）を型として検証するテストを追加する | `tests/output-lossless.test.mjs`, `tests/db-provenance.test.mjs` |
| P5 | 「N社握る者」を含む全人格で出力を再確認し、全テストを通す | 検証記録 |

### P1 の設計方針

PDFの紙面は二段組みで、抽出テキストの行順は紙面の視覚順と一致しないことがある。
そのため行単位の厳密な再構築は行わず、次の方針をとる。

- 紙面見出し `「〇〇の人格」` を人格レコードの境界として使い、
  各人格に対応する紙面テキストの塊（ブロック）を作る
- 照合は「DBの本文が、その人格のブロック内に部分文字列として実在するか」で判定する
- 比較時は句読点・空白・全角半角の差を正規化する（PDFのレイアウト由来の差を許容）
- 自分のブロックに無いが他のブロックにある本文は、用語集や他頁からの正当な引用として
  別区分で報告し、どこにも無い本文だけを破損候補とする

この方針は「転記漏れ」は検出しないが、「原典に無い文字列の混入」＝
今回の寸断・断片流入を確実に検出する。目的に対して十分である。

### P3 の判断基準

- PDF紙面に正しい本文が読み取れる場合は、その本文へ修正する
- 用語集（紙面305〜306等）に定義がある固有バフは、定義本文を採用する
- PDFが物理的に判読できない、または原典自体が省略している場合は、
  例外として `data/provenance/exceptions.json` に人格名・項目・理由を記録する
- 原典の記載が複数の欄に分かれている場合は、欄をまたいで連結せず、
  紙面と同じ欄へそれぞれの本文を収める（例: [蝶] と [生きた蝶]）
- ルールの解釈に踏み込む書き換えは行わない（非目標）。
  例えば「（最大10）」が効果上限か累積上限かは紙面から一意に定まらないため、
  用語集へ揃えるのは説明文だけに留め、上限値（`max`）は変更しない

- `node tools/provenance/audit-output-lossless.mjs` が、検出0件を報告する

## 結果（Result）

完了条件をすべて満たした。

| 段階 | 着手前 | 完了時 |
|---|---|---|
| 第3段階（出力生成） | 破損 59件 / 監査指摘 91件 | 0件（照合本文 4030件） |
| 第1段階（DB本文） | 要修正 68件 | 0件 |
| 第2段階（検証） | 原典照合なし（第1段階の68件を全て見逃していた） | 原典PDFとの照合を回帰テスト化 |

- 第3段階の原因は `ROUND_STAGE_MARKER` が `\d+R` の手前で無条件に段落を切っていたこと。
  `[1R]`（持続表記）と`（1Rに2回）`（回数制限）まで分断していた。
  括弧の深さを見る単一のスキャナ（`scanEffectParagraphs`）へ統合して解消した。
- 第1段階の修正は `tools/provenance/repairs.json` に88件（40人格）を記録した。
  各件に出典紙面・理由・修正前後を持ち、`before` が現在のDBと一致しなければ適用を中止する。
- 上限値（`MAX_MISSING` / `MAX_TRUNCATED`）は両方0に固定した。
  今後この値を緩めることは、調査未了の状態を隠すことにあたるため行わない。

### 再発防止の要点

監査側が「何も検出しない」状態になっていないことを、次の方法で確かめている。

- 修正前の `js/generator.js` に対して第3段階の監査を実行し、91件を検出することを確認
- 正しい本文をわざと途中で切って第1段階の監査を実行し、切断として検出することを確認

この確認を伴わない「0件」は、監査が機能している証拠にならない。
