# 抽出器レビュー — 到達点と、次に解くべき課題

パック第一弾（244頁）をDBへ取り込む作業を通じて分かったことをまとめる。
この文書の目的は二つある。

1. いま何が保証されていて、何が保証されていないかを明示すること
2. 「一つの抽出器で今後の追加データを全て賄う」ために、次に何を直すべきかを示すこと

---

## 1. いま保証されていること

### 監査は5本あり、いずれも欠陥を注入して検出を確認している

| 監査 | 問い | 現在 |
|---|---|---|
| `audit-db-text` | DB本文は原典に実在するか。途中で切れていないか | 0件 |
| `audit-db-paragraphs` | DBの改段位置は原典と一致するか | 0件 |
| `audit-db-severed` | DBの改行は原典の一文を断ち切っていないか | 0件 |
| `audit-output-lossless` | 出力生成が本文を壊していないか | 0件 |
| `audit-output-paragraphs` | 4つの出力経路で段落構造が保たれるか | 0件 |

加えて抽出時の照合 `verify-pack-extract.mjs` が5検査すべて0件。

**「0件」に意味があるのは、欠陥を注入して検出を確かめた場合だけである。**
この原則は今回の作業で3度救われた。詳細は 4節。

### 監査の方向を両方向そろえた

DB→原典の照合だけでは、**落ちた本文**を原理的に検出できない。
DBに無いものは照合の対象にならないからである。

実際、6頁にわたる人格（蜘蛛の巣 人差し指の親方）の紙面157〜159が
抽出範囲から外れ、固有バフ9件がまるごと落ちていたが、監査は0件を報告していた。

`verify-pack-extract.mjs` の検査5（原典→抽出）を追加して塞いだ。
この検査だけは 0 が意味を持つ。

## 2. 今回見つかった欠陥の分類

### 2.1 組版の読み違え（抽出器の欠陥）

原典の紙面から段落を復元する際、「行末の余白に次の行の先頭文字が入るか」で
折り返しか段落境界かを判定している。この判定が破れる型が5つ見つかった。

| 型 | 件数 | 根拠にしたもの |
|---|---|---|
| 欄見出しが前段落に貼りつく | 7 | 見出しの形（`[名前] 最大N バフ`）|
| 括弧書きの補足が切り離される | 36 | 丸括弧だけで閉じた短い行 |
| 発動タイミング見出しが連結される | 14 | `data/timing-markers.json` の語彙 |
| ダイス行見出しが連結される | 8 | `2d7+2：` の形 |
| 括弧が閉じないまま段落が切れる | 27 | 括弧の対応 |

**重要な点: このうち多くは基本ルールブックにも潜んでいた。**
パックを追加したことで初めて表に出たのであって、新規データ固有の問題ではない。
誰も検査していなかったから見えていなかっただけである。

### 2.2 なぜ字幅だけでは決められないのか

余白と必要幅の差の分布を測った（pack1 全行）。

```
-1.0 ############################################################ 270
-0.8 ############################################################  94
-0.3 ###########################################                   43
+0.5 ##########################                                    26
+1.7 ############################################################  95
```

**自然な切れ目が存在しない。** 0.43pt や 0.51pt の差で判定が反転する箇所が
実在し、それは組版の丸め誤差と区別できない。

閾値（`WRAP_ROOM_RATIO`）をどこに置いても、必ず誤る箇所が残る。
そこで「本文の形」という原典由来の根拠に切り替えた。
これは推測ではなく、原典の文字そのものである。

### 2.3 DB側の欠陥

| 対象 | 内容 |
|---|---|
| 夜明事務所代表 S3 | `火傷付与。⏎ 量増加1を付与` → 原典は一文 |
| ワザリングハイツ | `だけ減少 ⏎ （最低7）` → 原典は一文 |
| E.G.O 2件 | 2つの効果が1行に連結 |

いずれも `repairs.json`（181件）に根拠つきで記録し、再現可能な形で適用している。

## 3. 次に解くべき課題（今回は持ち越し）

### 3.1 `is_wrapped` に例外規則が積み上がっている ★最重要

現在の判定はこうなっている。

```python
def is_wrapped(row, next_row):
    if splits_a_word(...):        return True    # 語中で割れている
    if has_unclosed_bracket(...): return True    # 括弧が閉じていない
    if starts_a_field(...):       return False   # 欄見出し
    if starts_a_clause(...):      return False   # 発動タイミング見出し
    if starts_a_dice_row(...):    return False   # ダイス行見出し
    if continues_previous(...):   return True    # 括弧書きの補足
    return room < needed          # 字幅
```

**この形は健全ではない。** 例外が6つあるということは、
最後の字幅判定が本質的に不完全だということである。
新しいデータが来れば7つ目、8つ目が要る。
「一つの抽出器で全て賄う」というご要望に対して、この構造は逆行している。

**考えるべき方向**

字幅は「行がどこで終わったか」しか答えない。
求めているのは「文がどこで終わったか」である。この二つは別物であり、
前者から後者を導こうとしている限り例外は増え続ける。

段落の判定を次の二層に分けるのが筋だと考える。

- **第1層（確実な根拠）**: 罫線・欄・節見出しといった組版の構造
  紙面が明示的に区切っている境界。ここは推測が要らない。
- **第2層（本文の形）**: 見出し語・括弧の対応・語の連続性
  第1層で決まらない箇所だけを、本文の形で決める。

いま「例外」と呼んでいるものは、実は第2層の**本体**である。
字幅を主・形を例外としている現在の構造が逆で、
形を主・字幅を最後の手段とすべきではないか。

この組み替えは影響範囲が広く（全3冊・約800頁の再抽出と全監査の再確認）、
今回のデータ追加と同時にやるべきではないと判断して見送った。

### 3.2 見出し語の語彙が構造化されていない

`data/timing-markers.json` に46語を集約し、JS（出力の行分割）と
Python（原典の段落復元）が同じファイルを読む形にした。
これで語彙のずれは防げる。

しかし語彙そのものは、原典を走査して見つけた語を足す形で増えている。
新しい語（例えば新パックの新しい発動条件）が来たときに、
**足し忘れても誰も気づかない。**

原典から「段落の先頭に立つ〜時/〜前/〜後」を自動で抽出し、
語彙に無いものを報告する検査があってよい。

### 3.2.5 ショップ節（サポートパッシブ・精神）がDBへ未反映 ★次にやる

抽出は動いており、`data/provenance/pack1-extracted.json` に
サポートパッシブ27件・精神5件が入っている。

**まだDBへ取り込んでいない理由**は二つある。

1. 照合側（`verify-pack-extract.mjs` の `reassembled`）が、この2種の
   レコード形からテキストを組み立てられない。網羅性の検査（検査5）を
   通せないまま取り込むと、取りこぼしがあっても気づけない。
2. 本文列が均等割り付けで組まれており、行末の余白が
   字幅をわずかに上回る（6.45pt / 6.00pt）。現在の判定では
   折り返しを段落境界と誤り、効果の文が途中で切れる。

   ```
   鈎事務所所属人格のみ発動。自分より速度が高い     余白6.45pt ← 折り返しなのに切れる
   敵がいるなら、戦闘開始時にクイック1～2を得て
   ```

   欄の右端を縦罫線（227.9）から取っているが、本文が実際に到達する
   右端は 225.31 で、2.6pt の内側にある。この差がそのまま余白へ
   上乗せされ、閾値をまたいでいる。
   **縦罫線は欄の境界であって、本文の右端ではない。**

   なお 2.2 で述べたとおり、閾値を動かして直すのは筋が悪い。
   3.1 の構造の組み替えと合わせて解くべき問題である。

取り込みを急いで検査を素通りさせるより、検査を用意してから入れる。
それまで `data_pages` にショップ節の紙面を申告していない
（申告すると検査5が65件を報告し、本当の取りこぼしがその中に埋もれる）。

### 3.3 抽出器が人格・E.G.O・ショップで別々に書かれている

`extract_pack_data.py` の中で、

- 人格 … 罫線帯 + 列（x0）+ スキル番号の対応
- E.G.O … 紙面単位 + `No.101 100欠` 行の検出
- ショップ … 罫線帯 + 縦罫線による3列分割 + 本文先頭による件の区切り

と、3つの読み方が並立している。共通しているのは
「罫線帯で区切り、列で振り分ける」という骨格だけである。

表の型を宣言的に書けるようにして、
個々のデータ種別は「どの列に何があるか」の記述だけで済ませたい。
そうすれば新しい表（次のパックの新カテゴリ）が来ても、
コードではなく記述を足すだけになる。

### 3.4 静かに壊れる監査

今回いちばん危なかった問題。

紙面見出しに `SECTION` の印を足したとき、読む側2か所のうち
片方の正規表現を古いままにした。すると紙面の区切りを見失い、
**監査は例外を出さず「0件」を報告した。**
比較する相手がいなくなっただけだったからである。

`tests/corpus-format.test.mjs` を追加して、
読む側すべてが同じ紙面数に届くかを検査するようにした。
回帰を注入して検出を確認している（378 → 358 で失敗する）。

ただしこれは今回の型を塞いだだけである。
**「壊れたまま問題なしと言う」型の検査は、他にもありうる。**
監査が「何件を照合したか」を常に報告し、
その数が急に減ったら気づける仕組みが要る。

## 4. 作業上で繰り返しつまずいた点

### 4.1 「0件」を成果と早合点しかけた（3回）

- 検査5を足す前、6頁人格のバフ9件が落ちていたのに0件だった
- `MAX_BLOCK_PAGES = 2` で照合範囲が足りず、8件を誤検出していた
- `SECTION` 印で紙面の対応が壊れ、0件になっていた

いずれも**欠陥を注入して初めて分かった**。
0件を報告に書く前に、必ず注入して検出を確かめること。

### 4.2 監査を緩めるときは、必ず再度注入する

誤検出を消すために判定を緩めると、本物まで通ることがある。

- `audit-db-severed` で「段落を丸ごと含むなら正しい」を足したら、
  行見出し `マッチ勝利時` が独立段落として存在するせいで、
  文の途中で切れた断片まで通した
- 「断片が段落の先頭から始まるなら正しい」を足したら、
  まさに分断である前半が通った（値の最後の行かどうかで区別して解決）

緩めた直後に注入テストをやり直すこと。3回とも、これで見つけた。

### 4.3 同じ語彙・同じ判定を2か所に書かない

- 発動タイミング語が JS だけにあり、Python で必要になった
  → `data/timing-markers.json` に集約
- 括弧の対応検査が監査とテストに二重に書かれており、片方だけ直した
  → テスト側も同じ判断（原典の誤記は分断ではない）に揃えた
- 紙面見出しの正規表現が2か所にあり、片方だけ直した
  → `tests/corpus-format.test.mjs` で検出できるようにした

3回とも同じ型である。**二重に書いた時点で、いつかずれる。**

### 4.4 `\u` エスケープで字を間違えた（3回）

`\u6589`（斉）と `\u65ac`（斬）を3度取り違えた。
以後、ソースには日本語の文字をそのまま書くことにした。
エスケープは読めないので、間違いに気づけない。

### 4.5 「原典が正しい」と決めつけない

原典にも誤記がある。

```
舞台開始時、自分の弾丸を[LCA亀裂弾」へと[弾倉変換]。
                              ^^^^^^^^ 開き [ に対し閉じ 」
```

DBはこれを忠実に写しており、出力も入力と一字一句同じ。
これを「分断」として報告し続けると、直しようのない指摘が残り、
本当の分断が埋もれる。
**分割が壊したのか、もともとそうなのかを区別する**必要がある。

字幅を主・本文の形を例外とする現在の構造を、
組版の構造を主・字幅を最後の手段とする形へ組み替える必要がある。
