# LIMBUS BUILD TERMINAL 全UI・操作性監査（2026-11-01）

## 結論

主要な操作経路はPC・タブレット・スマートフォンのChromium実ブラウザで踏破し、画面崩れや操作性に関わる問題をPR #493で修正した。追加axe診断で見つかったスキル空状態のキーボード操作不可と複数の色コントラスト不足も、同PRで修正・回帰防止する。初回の主な問題は4系統（画面遷移時のスクロール残留、スマートフォンのアカウント操作、人格お気に入り、残高ナビゲーションのタップ領域）。追加診断ではCCFOLIAプレビュータブ、リザルト並び順、抽出パック選択、フォームボタン等の小さな操作面も検出し、40pxを確保する対象を分類して追加修正した。

自動監査はChromiumでPC 1440px、タブレット1024px、スマートフォン390px・320pxの4 viewportを通し、画面撮影時に可視となったダイアログ／シート状態は4 viewportでaxe診断する。これとは別に、全26ビュー（ホーム1、ビルド9、ショップ7、記録7、設定1、使い方1）を4 viewport（1440／1024／390／320px）でaxe診断し、計104状態を走査する。critical／serious違反、または本文H1不足が1件でもあればCIを失敗させる。ダイアログ／シートの診断集計と全画面診断集計はmanifest上で別フィールドに保存し、母数を混同しない。実機Safari／Firefox、200%／400%ブラウザ拡大、実スクリーンリーダーでの確認は未完了であり、WCAG適合や全ブラウザでの完全性を保証するものではない。

## 監査範囲と方法

PlaywrightでPC 1440x1000、タブレット1024x768、スマートフォン390x844・320x640を検査。スマートフォンは `hasTouch: true` にし、操作ヘルパーは `locator.tap()` を使ってタッチ経路を通す（通常クリックで代用しない）。SINNER SELECT、全ビルドタブ、基本情報・ST・ラベル・CCFOLIAプレビュー、ショップ6分類、所持ライブラリ6分類、リザルト、設定の開閉項目、取り込み、共有、検索、保存・復元、確認ダイアログ、ホバー、キーボードフォーカスを巡回した。

QAアカウント・取得履歴・報酬は使い捨てデータで検証し、利用者の実データは変更していない。所持人格には旧同期表示名と、それより新しい保存ビルド名・HP／SAN／耐性・パッシブ・スキル・固有バフを持つ検証用人格も追加し、カード名と詳細ダイアログの実表示を検査する。SINNER SELECTの再選択はカードの実タップだけで通し、アプリ内部イベントで直接画面遷移させるフォールバックは置かない。新規作成も画面フォームの送信結果だけで判定し、作成APIを直接呼ぶ救済処理は置かない。インポート／共有の確認状態は撮影したが、適用・外部公開などの破壊的操作は行っていない。

最新の回帰監査は545スクリーンショット・4 viewport・148操作。必須キャプチャ漏れ、操作失敗、コンソールエラー、HTTPエラー、ページ例外、水平はみ出し、重大レイアウト警告はいずれも0件。画面の存在確認だけに偏らないよう、スクリーンショットとDOMの実測値を併用した。全画面axeは104/104ビュー幅状態、画面撮影時のダイアログ／シートaxeは133状態で実行し、結果は別々に集計する。初回詳細監査では全画面に126件、可視オーバーレイに114件の表示ラベル不一致ノードが見つかったが、いずれも共通ヘッダー／カテゴリカードの3つの原因に集約されたため共通部品側で修正した。

## 検出した問題と修正

### P2 — 画面切替後に前画面のスクロール位置が残る

中央の `.focus` は画面切替後も同じDOM要素を使い続ける。従来の `SET_UI currentSection` は `scrollTop` を初期化しないため、長い画面の下部から別画面へ移動すると、次画面の先頭・見出しが隠れた位置で表示され得た。

**修正:** 画面と主要サブ画面（所持タブ、ショップ分類、設定詳細、基本情報内タブ）のルートキーを追跡し、キーが変わったときだけ中央スクロールを0へ戻す。検索文字、入力、フィルターなど同一画面内の更新では位置を保持する。監査ハーネスに「ホームの末尾からショップへ移動し、先頭に戻る」回帰検査を追加。

### P2 — スマートフォンのアカウント編集・削除ボタンが小さい

アカウントカード内の `.acct-icon-btn` は28x28 CSS px。編集／削除を誤タップしやすく、旧チェッカーの検査対象にも含まれていなかった。

**修正:** 640px以下で編集・削除の操作領域を40x40 CSS px以上に拡大。カードの情報構造とデスクトップ寸法は維持。

### P2 — スマートフォンの人格お気に入りが小さい

人格カードの `.p-fav` は24x24 CSS pxで、旧タップ領域監査の対象外だった。

**修正:** 640px以下でお気に入り操作の領域を40x40 CSS px以上に拡大。星アイコン自体の見た目と通常幅のレイアウトは維持。

### P2 — CCFOLIAプレビュー切替タブと記録フォームの操作面が小さい

追加した全操作要素のDOM診断で、プレビュー切替タブが29px、リザルト並び順が38px、抽出パック選択欄が32pxとなる状態を検出した。小さい選択欄やタブはモバイルで押し損ないやすく、既存の検査セレクターにも漏れがあった。

**修正:** プレビュー3タブ、記録の並び順・抽出パック選択、ボタン／送信ボタン、モバイルフォーム入力欄を40px以上に統一。既存コンポーネントCSSの後から高さ指定が上書きされることが分かったため、全リンクCSSより後に最終モバイル補正を置き、実際の描画寸法を再検査する構成に改めた。

### P2 — スマートフォン上部の残高ナビゲーションが小さい

監査スクリーンショットのDOM寸法から、残高表示ボタンは390px幅で132x25 CSS pxと確認した。単なる数値表示ではなく、押すと記録・収支画面へ移動するボタンであり、他の主要タップ操作と比べて高さが不足していた。また旧チェッカーの明示対象から漏れていた。

**修正:** 640px以下で `.topbar-balance` の最小高さを40pxに設定し、タップ領域監査の対象へ追加。

### P2 — 320px幅で人格取得照合の開閉見出しが小さい

「PERSONA AUDIT／人格取得の照合」の開閉見出しは320px幅で高さ約34.8 CSS pxだった。全操作要素の補助計測には出ていたが、既知操作対象のセレクター一覧にsummaryが含まれず、40pxタップ領域のゲートを通過してしまっていた。

**修正:** 640px以下で当該summaryの最小高さを40pxへ拡大し、`.ledger-persona-audit-disclosure > summary` を実測タップ領域のゲートへ追加。診断ログと合否判定の対象を一致させる。

### P2 — ブラウザ起動時の404を特定できない

axe用の初期ブラウザ起動時にリソース404が1件検出されたものの、従来ハーネスはconsole文字列しか保存せずURLが失われていた。入口ページにファビコン指定もなく、ブラウザ既定のファビコン要求とアプリ資産の404を区別できなかった。

**修正:** メイン・共有・モバイルプレビューの各入口へ軽量なインラインSVGファビコンを指定。Playwright共通ハーネスはHTTP 4xx／5xxのURLも起動エラーへ記録し、再発時に対象リソースを特定できるようにする。

### P1相当 — 共通ボタンの表示ラベルと読み上げ名が一致しない

全26ビュー×4幅のaxe検査で、`label-content-name-mismatch` が126ノード分記録された。詳細を集約すると、原因は共通UIの3系統に集約される。検索ボタンは可視ショートカット `⌘K` をアクセシブル名に含めていない。JSON出力ボタンは表示文言「JSON出力」に対して「CCFOLIA JSONをコピー」だけを名前に設定していた。ショップ分類カードは、カード内のカテゴリ名・説明・件数よりも「カテゴリを開く」という aria-label を優先していた。

**修正:** 検索ボタンの名前へ可視ショートカットを加え、JSON出力ボタンの名前を表示文言から始める。ショップ分類カードの aria-label を除去し、カード内の見出し・説明・件数から自然にアクセシブル名を構成する。画面ごとの複製修正ではなく共通部品の3箇所で全状態に対応する。axe全画面・4幅の再実行で serious/critical 0を確認するまでマージしない。

## 監査基盤の改善
- モバイル幅でCCFOLIAプレビュー切替タブ、記録の並び順、抽出パック選択、ボタン、送信ボタン、フォーム入力欄の実タップ領域を40px以上へ補正。最終スタイルは外部コンポーネントCSS読み込み後に適用し、CSSカスケードによる上書き漏れを防ぐ。
- タップ領域の診断では、対象セレクターだけでなく全ボタン・リンク・入力・summaryの小領域もタグ・クラス・実寸で記録。ネイティブのチェックボックス／ラジオや意図的な小型装飾を一律に拡大せず、役割別に判断する。
- UI撮影中に可視ダイアログ／シートがある場合は、その表示状態でaxeを実行し、対象画面・viewport・違反ノードをmanifestに保存。別工程でも全26ビュー×4幅のaxe詳細をJSON成果物へ保存する。

- スクリーンショット／操作監査に画面切替後のスクロール位置テストを追加。
- アカウント編集・削除、人格お気に入り、残高ナビゲーションを40pxタップ領域監査へ追加。
- 既知セレクターに依存する監査だけでは新規UIを見落とすため、画面内に実際に存在するボタン・リンク・入力・summaryもDOM診断データへ記録するよう変更。40px未満を一律に失敗扱いせず、タグ・クラス・画面内座標で分類できるようにした。
- 利用者向けアクセスカウンター撤去後も残っていた、監査ハーネス内の旧カウンターAPIモックを削除。

### 追加axe診断で検出した問題と修正（PR #493内）

最初の26ビュー詳細診断では、合計24ノード（重大・深刻）が見つかった。内訳は、スキル未登録時の旧deckスクロール領域1件、罪属性の赤／紫チップのコントラスト不足12件、精神の「混乱」タグのコントラスト不足11件。いずれも診断上の画面・DOMノードまで確認した。

**修正:**
- スキル未登録状態を、編集可能時にはキーボードでも実行できる実ボタンへ変更。旧5列横スクロールを解除し、単一列の空状態にする。閲覧モードはネイティブのdisabledボタンにして、操作不可を視覚・支援技術双方へ伝える。
- 罪属性チップおよびE.G.O資源カウントの赤・紫文字を明るく調整。罪属性自体の色は背景・枠に残し、色による識別性は維持する。
- 精神の「混乱」タグ文字を明るく調整し、背景とのコントラストを確保する。
- 26ビュー詳細axe診断でcritical／serious違反をCIゲート化。診断失敗時もJSONをartifactへ保存して、問題箇所を確認できるようにする。
- 画面全体のaxeとダイアログ／シート状態のaxeは別々に集計する。従来の画面全体の違反ノード数と誤解される集計名を廃止し、後者をoverlay専用と明示する。

### 修正後のコントラスト目標
- 憤怒チップ：4.38:1 → **6.53:1**
- 傲慢チップ：3.45:1 → **8.72:1**
- 混乱タグ：3.41:1 → **6.01:1**

色値は既存の暗色背景で測定したCSS前景色／背景色の組合せに基づく。最終的な合否はCI上のChromium axe再実行で確認する。

### P1 — 記録・所持品トップの「取り込みを開始」がボタンに見えない

記録ハブの見出し右側にある「取り込みを開始」は、動作自体はボタンである一方、primary という単独クラスがデザインシステムの btn / btn-primary に一致せず、共通ボタンの背景・枠・余白が適用されていなかった。実画面では高さ18px程度の通常文字列に見え、主要操作として認識しづらい。

**修正:** 共通の btn btn-primary を適用し、record-import-launch を付与。スマートフォンでは最低40pxの操作高さを確保し、タップ領域チェッカーの明示対象へ登録した。

### P2 — 起動時SINNER SELECTの「編集」が小さい

アカウント管理ダイアログ内の編集ボタンは別途拡大されていたが、起動直後のゲート画面にある .acct-gate-edit-btn はそのCSS対象外で、実測58×30 CSS pxだった。管理画面と起動画面で同じ「編集」操作なのに押しやすさが異なり、既存の明示タップ領域検査も見落としていた。

**修正:** スマートフォンで最小幅72px・高さ40pxに拡大。ゲート画面から実際に編集フォームを開くPlaywright操作と寸法検査を追加し、閉じる操作でゲートへ戻ってからアカウント選択を続ける。

### P2 — サポート装備枠の解除「×」が小さく、並べ替えと近接する

ビルドのサポート欄にある解除ボタン .spp-slot .rm は20×20 CSS px。並べ替え矢印も近くに配置されるため、スマートフォンでは誤タップしやすい。解除対象が視覚的にアイコンだけで、支援技術向けの名前も不足していた。

**修正:** スマートフォンでは解除ボタンの操作面を40×40pxへ拡張し、矢印群をさらに左へ離して当たり判定の重複を防止。通常サポート／死亡後サポートとも「どのサポートを枠から外すか」を示す aria-label を追加。QA用の装備済み枠を実際に解除し、枠数が正確に1つだけ減ること、解除ボタンと並べ替え操作が重ならないことをPlaywrightで検査する。

### 追加監査で分かったこと

今回の3件は、従来の「全ボタン一般」では拾えていない見た目・操作対象の不一致だった。監査対象は、汎用ボタンだけでなく、画面固有の主要CTA、起動ゲート内の操作、カード内のアイコン操作、装備スロット操作まで列挙する。全操作要素の補助計測値も記録し、明示チェック対象から漏れた要素を次回レビューで拾えるようにする。
### 追加の目視監査で検出した問題と修正（320px幅・編集モード）

#### P2 — 320px幅でサポート装備枠が2列のままになり、枠名が縦に折り返される
320px幅では2つのサポート枠を横並びに保つため、各枠が細くなり「スロット 1」の文字が1文字ずつ縦に折り返されていた。ページ全体の横はみ出しやボタン寸法だけを測る検査では検出できず、画面画像の目視で発見した。

**修正:** 360px以下では装備枠を1列に縦積みし、各枠の幅を確保する。Playwrightで実際のgrid列数、各枠の幅、枠番号ラベルの高さを測定し、再発時はCIを失敗させる。

#### P2 — アカウント編集フォームにオンライン保全パネルが常時表示され、編集領域を圧迫する
SINNER SELECTの既存アカウント編集時、共有URL・アカウント名・用途・アイコンを編集するフォームの直下にオンライン保全パネルが残り、320px幅ではフォームの下部が大きく隠れていた。アカウント新規作成時には同じ保全パネルを退避していたが、既存アカウント編集時には適用されていなかった。

**修正:** .acct-grid.is-editing の間はアカウント管理パネル直下のオンライン保全パネルを非表示にし、編集をキャンセル／保存して一覧へ戻ると再表示する。ブラウザ監査でも編集状態に保全パネルが残っていないことを実測する。

## 良好だった点・維持事項

- 主要4幅の撮影対象でドキュメント横はみ出し・重大なレイアウト警告を検出しなかった。
- SINNER SELECTのアカウント一覧・編集カードはスクロール領域が確保され、カードと操作ボタンの重なりは見られなかった。
- ショップはカテゴリ選択ハブから各分類へ移動でき、戻る導線を保持。人格カードはビルド画面のカード表現と統一されている。
- ビルド9タブはスマートフォンで複数行グリッドになり、タブが横方向に押し潰されない。
- 設定の開閉項目、取り込み先選択、共有方法、保存データの範囲確認、検索、ホームのランチャーなどを撮影・操作確認した。
- 取り込み・共有・保存の確認画面は使い捨てQAデータで開閉し、実データへの適用や外部公開はしていない。

## 残課題と監査の限界

1. **アクセシビリティ:** 全画面axeは26ビュー×4 viewport（1440／1024／390／320px）の104状態を検査し、critical／serious違反と本文H1不足をCIゲートにする。ダイアログ／シートaxeは撮影時に可視となった133状態を4 viewportで検査する。共有UIも空の共有入口と実生成シートを4幅で検査し、折り畳み展開・検索結果・個人メモを含めた20状態を追加する。全メニュー・ポップオーバー・バリデーション状態の全組合せ、フォーカストラップ、読み上げ順、Escape復帰、スクリーンリーダー実機での確認は別途必要。
2. **画面幅・拡大:** 320pxの狭幅でも主要操作シナリオを巡回した。ただし200%／400%の実ブラウザズーム操作と、その状態での全フォーム内容の再確認は別途必要。
3. **ブラウザ・実機:** Chromium中心。実機iOS Safari／Android Chrome、Firefox、Safariのフォント・スクロール・タッチイベントは検証していない。
4. **操作領域の分類:** 全操作要素の小領域を診断ログに残すようにしたが、すべてを40px以上へ機械的に拡大するのは適切でない。文字入力・タグ・密集した表の操作などは周辺余白や誤操作リスクを見ながら分類し、修正対象を追加する。
5. **共有ビューア:** `share.html` の空状態と、通常人格・E.G.O・サポートを含む実生成シートを1440／1024／390／320pxで検査する。生成シートでは折り畳み展開・検索結果・個人メモまで含めた20状態をaxeへ通す。実際の外部共有URL・ネットワーク保存先の失敗応答、読み上げ順、200%／400%拡大、共有先端末でのメモ保存は別途E2E／実機確認が必要。モバイルプレビューは専用構造テストを持つが、外部ブラウザ実機の確認は未完了。
6. **同期アカウント:** QA用に旧roster表示名と新しい保存buildが共存する同期人格を投入し、所持一覧の名称、HP／SAN／耐性、パッシブ、スキル、固有バフを詳細ダイアログで検査する。実ユーザーのクラウド同期データを使った全パターン、および20アカウント上限での負荷検証は未完了。

以上から、主要UI経路のレイアウト／操作回帰は良好だが、「全ブラウザ・全アクセシビリティ条件で不具合ゼロ」とは判定しない。
