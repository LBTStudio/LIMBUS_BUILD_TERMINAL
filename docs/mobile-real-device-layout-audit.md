# 実機相当モバイルUI監査（ローカル）

## 確認環境

Chromiumのiframeビューポートを利用し、iPhoneの代表的なCSS表示領域へ直接合わせた。スクリーンショットはブラウザ外側の確認フレームではなく、内部アプリのCSS表示領域を基準に評価する。

## 初回所見

844×390pxではヘッダー内の主要ブロックに物理的な矩形重なりはない。しかし、ブランド、検索、JSON出力一式、操作・保存の合計幅がほぼ横幅を使い切っており、より狭い横向きiPhone（例: 667×375px）では、`overflow: hidden`により後半操作が切れる危険がある。

| 対象 | 測定値（844×390px） | 所見 |
|---|---:|---|
| ブランド | 171px | 横向きスマートフォンでは情報量が過大 |
| 検索 | 153px | ショートカット表示を含み、必要以上に幅を使う |
| JSON出力一式 | 364px | 高頻度の直接操作としては過密 |
| 操作・保存 | 101px | 右端に残るが、小型横向きでは切れるリスクがある |

下部ナビゲーションは844×390pxで画面内に収まる。次は667×375px相当でヘッダーの実際の切れ・重なりを測定し、低い横向き画面専用のコンパクトヘッダーを導入するか判断する。

## 小型横向きiPhone相当（667×375px）

測定上は、ヘッダーの4ブロック（ブランド、検索、JSON出力一式、操作・保存）と下部12ナビ項目に矩形の重なり・画面外への切れはなかった。ただし、JSON出力一式が322pxを占有し、390pxの高さでは本文よりも操作群が強く見える。スクリーンショット上でボタンが重なって見える主因は、物理的な衝突ではなく、この高密度なヘッダー内操作群である。

改善方針は、低い横向き画面では直接表示のJSON出力一式を隠し、既存の「操作・保存」入口へ集約することとする。これにより、すべての機能を維持しつつ、ブランド・検索・操作入口の3要素だけをヘッダーに残す。

実装後の667×375px再測定では、`topbar-actions`は非表示となり、ブランド、検索ショートカット、操作・保存だけがヘッダー内に残った。ヘッダーは幅667px内、下部12ナビ項目はすべて画面内、文書横幅も667pxで一致した。スクリーンショット上でも操作群どうしの重なりは見られない。

## 共有シート 390×844px目視確認

先頭サマリーは人格名、HP、SAN、同期00、MAXを一行群で確認でき、カードサイズも小型画面で収まった。一方で、既存の人格行が見出し下に残り、同じ人格名・同期情報が二度表示されている。これは情報量の増加ではなく重複であるため、先頭サマリーへ統合して下側の重複行を除去する。

統合後の390×844px再確認では、人格行は1件だけになり、人格名、HP 125、SAN 50、同期00、同期MAXが先頭領域に収まった。見出し下の人格名再掲はなく、ステータスカードはそのまま維持されている。

サポートパッシブは展開式を維持しつつ、展開後の各パッシブ内では`常時:`と`効果:`を同じ効果領域に連続表示する実装へ変更した。通常の縦スクロール操作で参照でき、常時効果と通常効果のカード間往復は不要になる。

展開状態を390px相当で再確認した結果、`常時: 戦闘開始時、味方全体に保護1を付与 / 効果: 味方が攻撃的中時、対象へ振動1を付与`が単一の効果ボックスへ表示された。効果本文の重なり・横切れは確認されなかった。
