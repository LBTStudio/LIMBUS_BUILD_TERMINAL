# ツール全体の多角監査（2026-10-23）

## 目的と監査範囲

LIMBUS BUILD TERMINAL の不具合を、画面・状態管理・データ取り込み・通帳計算・抽出乱数・ハッシュ検証・出力・キャッシュ・テスト網羅性の観点で点検した。

今回のコード監査では、実装と回帰テストの記述を相互照合し、再現条件がコード上で明確な欠陥を優先した。DOM を使った実ブラウザーの操作、複数ブラウザーでの視覚比較、実機スマートフォンでのタップ／スクロール、完全オフライン状態の試験は、この監査作業環境から直接実施していない。したがって「全バグなし」の証明ではなく、確認した問題・対処・残るリスクを記録する。

## 確認された不具合と修正

### 1. 高：抽出エンジンのSHA-256パディング境界が標準と不一致

**対象:** `js/gacha.js` の `sha256Bytes`、コミット→開示・HMAC検証に使うハッシュ。

**原因:** パディング後の配列長を `((((bytes.length + 9) >> 6) + 1) << 6)` で計算していた。この式は `bytes.length + 9` が64の倍数になる場合に、必要なブロック数より1ブロック多く確保する。したがって入力長が **55 + 64k バイト**（55、119、183…）の場合、長さフィールドが想定と異なるブロック末尾へ配置され、標準SHA-256と異なるハッシュを返す。HMAC内のメッセージや長い鍵のハッシュでも同条件が起き得る。

**影響:** 該当する長さのシード／メッセージではコミット値、抽選記録、署名や第三者検証の結果が標準実装と合わなくなる可能性がある。すべての入力で抽選が壊れるわけではないが、検証可能性の根幹にかかわる。

**修正:** パディング長を `Math.ceil((bytes.length + 9) / 64) * 64` に変更。空文字・既知ベクタ・マルチバイト・長文に加え、境界前後の複数長（54/55/56、118/119/120、182/183/184など）を `node:crypto` と比較するテスト、HMACのメッセージと長い鍵の境界テストを追加した。

### 2. 高：通帳の不正な数値入力をゼロと扱い、残高差分を誤推定

**対象:** `js/ledger-import-reconcile.js` の `normalize` / `hasNumber` / `reconcileResults`。

**原因 A:** `Number(value) || 0` により、`"abc"` などの不正入力が0へ変換されていた。その後の `Number.isFinite(normalize(value))` は0を有限数と判断するため、不正な残高が「残高0」として計算に入り、架空の支出や差分を出す可能性があった。

**原因 B:** LPと欠片に共通の `started` フラグを使っていた。最初の行でLPだけが入力済みでも両通貨の集計を開始済みと扱い、後の行で初めて入力された欠片残高を、過去の欠片残高が既知であるかのように差分計算していた。

**修正:** 厳密な数値パーサーを導入し、空欄／非数値を区別。不正な収入は明示的にエラー情報を返し、不正な現在残高は未入力扱いの警告を返す。カンマ区切りの妥当性も検証する。LPと欠片はそれぞれ独立した開始基準と直近残高を持つよう変更した。

**追加テスト:** 不正な文字列、異常な桁区切り、正しいカンマ区切り、LPのみ先に入力された履歴、非数値の収入を追加。

### 3. 中：既定のリザルト日付がUTC基準で前日にずれる

**対象:** `js/state.js` の初期作成、旧抽出チケットの移行記録、`ADD_RESULT` の既定日付。

**原因:** `new Date().toISOString().slice(0, 10)` はUTC日付を返すため、日本時間の深夜から午前9時前に操作すると、利用者の現地日付より前日が記録される。

**修正:** ローカル年月日から `YYYY-MM-DD` を生成する関数へ統一し、初期作成・移行記録・日付未指定のリザルトで使用。回帰テストを追加した。

### 4. 低：硝子窓URLが無効な場合のエラー案内に誤記

**対象:** `js/garasumado-roster-import.js` の共有URL検証。

**原因:** 不正なURLを貼り付けた場合の案内が「貼りってください」になっており、利用者が正しい操作を判断しづらい。

**修正:** 「貼り付けてください」に修正し、無効URLのエラー文面を回帰テストで確認するよう追加。

### 5. 高：作業状態JSONに含まれる複数項目が部分インポートで黙って落ちる

**対象:** `js/App.js` の `IMPORT_GROUPS` と `validateImportData`、`js/state.js` の `APPLY_PARTIAL` 許可リスト。

**原因:** エクスポートは `ui` 以外の state をJSONに含める一方、インポートはカテゴリに列挙された項目しか適用しない設計だった。点検では `initiative`、`initialItems`、`draws`、`favorites`、`historyRecent`、`gachaLog` がカテゴリ定義または許可リストから漏れていることを確認した。これらは有効なJSONであっても、インポート時に対象として認識されず、適用先の値が残るか履歴が失われる。

**影響:** 別端末への移行後に、イニシアチブ、初期所持アイテムの指定、抽選バッチの証明情報、抽選履歴、お気に入り、最近使った項目が元ファイル通りに復元されない。ファイルの構文検証では検出できないため、インポート成功の表示だけでは完全復元を確認できない。

**修正:** イニシアチブを基本情報へ、初期所持アイテムをアイテム群へ、抽選ログと検証バッチを抽選記録群へ、お気に入りと最近の履歴を独立カテゴリへ追加。reducerの許可リストにも `initiative`、`initialItems`、`draws` を追加した。併せてインポート前に配列型だけでなくレコード要素・抽選バッチの `records` も検証し、`null` やプリミティブ要素による正規化例外と証明データの静かな破棄を防ぐ。ソース監査テストと状態管理の復元テストを追加した。



### 6. 中：硝子窓URLの文字列検査が別ドメインを誤受理

**対象:** `js/garasumado-roster-import.js` の `parseShareUrl`。

**原因:** 以前は入力文字列のどこかに `garasumado` が含まれていれば、その後はホスト名を検証せず `/view/ID` を抽出していた。そのため、別ドメインのURLであってもクエリ文字列に `garasumado` が入っている場合や、似たホスト名を使った場合に、硝子窓のURLとして誤って受理される可能性があった。

**修正:** 公式ホスト `lbt-garasumado.vercel.app`（およびその `www` 形）を検証し、pathname が `/view/ID` または `/persona/view/ID` の形式であることを確認するよう変更。ID単体、スキーム省略、query/hash、コピー文中の括弧付きURLは維持しながら、他ホストと似たホスト名は拒否する。

**追加テスト:** 正規URL、人格URL、スキーム省略、query/hash、コピー文に包まれたURL、別ドメインのクエリに `garasumado` があるケース、類似ホスト名を検証する。

### 7. 高：Undo再生で抽選の所持品・費用まで復活し得る

**対象:** `js/state.js` の `useAppState().reseal` と抽選バッチのreducer。

**原因:** 以前は抽選証明と所持品／通帳の支出を同じ `ADD_DRAW_BATCH` が処理していた。Undoで抽選前の状態へ戻った後に封緘済みアクションを再生すると、所持追加・費用計上も再実行される。チケット消費が巻き戻っても取得品が復活するなど、無料取得や所持・会計の不一致につながり得た。

**修正:** 経済的な副作用はUndo可能な `APPLY_DRAW_BATCH` に分離し、証明は `ADD_DRAW_RECORD` で保存。Undo/Redoで封緘済み操作を再生する際は `proofOnly` として証明だけを保持し、所持・支払いは再適用しない。同一証明キーの二重登録も拒否する。

**追加テスト:** チケット抽選／LP購入を確定した状態からUndoを模擬し、所持・支出は巻き戻る一方、抽選証明と決定ログだけが残ることを検証する。

### 8. 高：非同期抽選確定が残高・費用記録・証明と不整合になる競合

**対象:** `js/OtherSections.js` の `commitDrawAsync`、`js/state.js` の `validateDrawBatchApplication`／`APPLY_DRAW_BATCH`／`ADD_DRAW_RECORD`。

**原因:** 外部ビーコン取得や署名待ちの間に残高が変わると、プレビュー時には足りていたチケット／LP／欠片が確定時には不足し得る。reducerが経済取引を拒否しても証明や決定ログを後から無条件に積めば、履歴だけが残る。さらに、呼び出し側の合計額だけを検査すると、封緘レコードに記録された費用と違う値を渡して支払いを迂回する余地がある。

**修正:** UIの確定直前とreducerの双方で残高・重複・証明キーを検証。バッチの各レコードのLP／欠片コストを合算して費用の正本とし、呼び出し側が渡す合計額と一致することを要求。不正なレコード・非整数費用・空バッチ・証明キー欠落・費用不一致・残高不足は拒否する。取引が受理された場合だけ一時的なproof keyを立て、続く `ADD_DRAW_RECORD` が証明と決定ログを同時に保存する。拒否された取引は所持・費用・証明・ログのどれも反映しない。

**追加テスト:** 確定待ち中の残高変更、チケット／通貨不足、合計費用偽装、費用の小数・不正値、証明キー欠落、重複バッチ、証明のみのUndo再生を回帰テストに含める。

### 9. 高：通帳の数値正規化が部分一致・負数・小数を通し、残高を誤算する

**対象:** `js/state.js` の `normalizeCurrency`／`normalizeTickets`、`js/ledger-import-reconcile.js` の `parseNumber` と `reconcileResults`。

**原因:** `parseInt("1200abc", 10)` のような部分一致は不正文字列を正規の金額にしてしまう。負のチケット消費数は収入から差し引く際に残数を増やし得る。さらに通貨・チケットは整数であるべきなのに、小数値を黙って切り捨てると原記録と残高が食い違う。

**修正:** 数字列全体と桁区切りを検証し、LP／欠片は非負の整数のみ受理。チケット数も非負の安全な整数だけを計上し、負数・部分一致・小数は0／未入力として扱い、通帳取込では不正な入力を明示的な警告へ分ける。

**追加テスト:** `"1200abc"`、`"3x"`、不正な桁区切り、負数、小数、LPと欠片の初回残高が異なる履歴を回帰テストに追加。

### 10. 中：配列形式としては有効なJSONでも、壊れたレコードをインポートできる

**対象:** `js/App.js` の `validateImportData` と部分インポート処理。

**原因:** `results: [null]`、`entries: ["broken"]`、`draws: [{records: []}]` などはJSONとしては有効。配列であることだけを検査すると、正規化の例外や抽選証明の静かな欠落、重複IDによる誤更新につながり得る。

**修正:** レコード配列と `roster` 配下の配列について、全要素が非nullのオブジェクトであることを適用前に検証。抽選バッチでは `records` 配列、各レコードの形状、`batchHash` または `commit` の証明キーを必須化。リザルト／明細の明示ID重複も拒否し、エラーにはフィールドと配列位置を含める。

**追加テスト:** null／プリミティブ要素、records欠落、証明キー欠落、重複IDを拒否し、正常な空保存や正規証明は受理することを確認する。

### 11. 高：旧抽出チケットの移行判定が、通常リザルトの金額一致で旧在庫を捨てる

**対象:** `js/state.js` の `normalizeStateShape` にある旧 `tickets` からリザルト収入への移行。

**原因:** 旧チケット在庫を移行する際、全リザルトの収入を調べてチケット数が一致する行が1つでもあれば、移行済みと判断していた。通常のシナリオ報酬が同じ枚数だっただけでも条件を満たすため、旧在庫のチケットをリザルトへ移さず失う可能性があった。

**修正:** `res-ticket-grant` の移行専用IDがある記録だけを重複移行防止の判定に使う。旧チケット件数は非負の整数かつ有効な種別（パック型はパック名あり）の行だけ移行する。パック名の欠落・端数など移行できない行は誤変換せず `tickets` に未解決データとして保持し、部分インポートの「抽選記録・旧セーブ移行データ」カテゴリにも含めて別端末へ運べるようにした。

**追加テスト:** 通常報酬と旧在庫が同じ枚数でも両方を維持すること、2回目の正規化で二重加算しないこと、未解決行が再読込後にも残ることを検証する。

### 12. 中：入れ子の人格スキル／保存ビルドが不正型だと、トップレベル検証をすり抜ける

**対象:** `js/App.js` の `validateImportData` と `js/state.js` の `sanitizeStateCollections`。

**原因:** 最初のインポート検証はルートの配列要素・`roster` 配列だけを確認していたため、`personaSrc.skills: "broken"`、`personaSrc.skills[0].dice: "broken"`、`roster.personas[i].build.skills: "broken"` のような入れ子構造が通過する可能性があった。正規化ではスキル配列の `.map()` やダイス配列が利用されるため、読み込み時の例外または空の効果行への誤変換につながり得る。

**修正:** インポート時に `personaSrc.skills`、`unique_buffs`、`keywords`、各スキルの `dice`、所持人格の `build` 内スキル／固有バフ等の配列型と要素を検証する。ローカル保存の読み込みでは、壊れた配列を安全な空配列へ正規化し、正常な要素と証明バッチ本体は可能な限り維持する。

**追加テスト:** 入れ子の不正配列をインポート前に拒否すること、壊れたローカル状態から有効な人格・明細・抽選ログを維持しながら正規化を完了することを検証する。

### 13. 中：選択抽出チケットが在庫に存在しても、抽選画面から使えない

**対象:** `js/gacha-tickets.js` の `drawN` と `js/OtherSections.js` の `GachaTicketsPanel`。

**原因:** 状態モデル・残高計算には `choice`（人格かE.G.Oを利用者が選べる共通チケット）が実装されている一方、画面と抽選エンジンの入口は、人格ルートなら `persona`、E.G.Oルートなら `ego` の専用チケットだけを参照していた。共通チケットしか持たない場合、在庫表示には現れても使う選択肢がなかった。

**修正:** 人格／E.G.Oルートで共通チケットを指定できるようにし、専用チケットと共通チケットの両方を持つ場合は使用する種類を選べるようにした。パック抽出では従来どおりパック名ごとの専用チケットだけを使う。確定処理には画面で選んだチケット種別をそのまま渡す。

**追加テスト:** 人格ルートで共通チケットから無料抽選を行い、封緘バッチが `core-ticket` と `method=ticket` で成立すること、UIが共通チケットの選択操作を出すことを検査する。

### 14. 中：テーマパック抽選の証明ハッシュがパック名を固定していない

**対象:** `js/gacha.js` の `batchRecordBody`／`finalizeBatch`。

**原因:** テーマパックの結果レコードはパック名を保持していたが、ハッシュ鎖を作る本文から `pack` が省かれていた。同じキャラクター名が複数パックに登場する場合、パック名を差し替えても当該レコードのハッシュが変わらず、抽選の出所を証明だけから検証できない可能性があった。

**修正:** 新しい証明ではパック名をレコード本体に含めてハッシュ化する。旧記録との互換性を守るため、`pack` フィールドを持たない過去レコードは従来のハッシュ本文のまま検証する。

**追加テスト:** 正常なテーマパック証明が検証を通ることと、レコードのパック名だけを差し替えると検証に失敗することを追加する。

### 15. 高：チケット種別／支払枚数が封緘バッチと一致することを保証できていない

**対象:** `js/state.js` の `validateDrawBatchApplication`。

**原因:** 取引検証はチケット残数を見ていたが、旧実装では支払うチケットの種類・枚数と封緘バッチの抽選種別・件数を十分に比較していなかった。別種類のチケットで異なるルートを確定する、記録件数より少ない枚数を消費する、あるいは共通チケットの消費指定を省く余地があった。

**修正:** `core-ticket`／`method=ticket` をチケット取引として扱い、チケット取引では全レコードがチケット方式であること、消費枚数がレコード件数と一致すること、バッチ種別とチケット種別が対応することを確認する。パック抽出では各レコードのパック名も指定パックと照合する。チケット取引に必要な消費指定がない場合や、通貨取引にチケット方式のレコードが混入した場合は、所持・費用・証明の確定を拒否する。

**追加テスト:** 支払指定なし、E.G.Oチケットで人格抽選、枚数の不一致、共通チケットでの有効な人格抽選を検証する。

### 16. 高：特異人格の抽選分岐・所持登録・価格段階が通常経路につながっていない

**対象:** `js/gacha-tickets.js` の `engineBatchN`、`js/gacha.js` の `drawBatch`、`js/state.js` の `rosterAddsFromDrawBatch`。

**原因 A — 分岐に到達しない:** 抽出ルートの説明とルール表は、通常人格ダイスの最大 +1 枠を特異人格へ分岐させる設計だったが、実際の画面から呼ばれる `engineBatchN` が `plusOne` をエンジンに渡していなかった。画面で抽選する経路では、特異人格チャンスを実質的に引けなかった。

**原因 B — 所持へ登録されない:** 特異人格の封緘レコードは `record.kind / item.kind = "specialPersona"` となる。一方、所持変換処理は `item.kind` が `persona`・`ego`・`themePack` のケースしか処理しておらず、特異人格を所持リストにも取得費用明細にも変換していなかった。

**原因 C — 次の抽選が無料のまま:** 価格段階は `own.personas.size`（通常人格だけ）を数えていたため、特異人格を先に引いても、同一バッチ内の次の人格抽選が無料のままになる可能性があった。UI側の表示は所持人格の総数を基準にするため、表示と実際の請求も不一致になり得た。

**修正:** 通常人格ルートから最大 +1 の分岐を明示してエンジンへ渡す。特異人格レコードを `mode:"t"` の所持人格へ変換し、取得費用を同じ明細へ記録する。バッチ内価格段階を通常・特異の合計所持数から計算し、各取得後に1ずつ増やす。

**追加テスト:** 強制した最大出目で特異人格→通常人格の順を再現し、初回0LP・次回100LP・残高不足で停止すること、特異人格の所持登録と通帳合計100LPが封緘レコードの費用合計と合うことを検査する。

### 17. 中：ハッシュ鎖の整合だけなのに、一覧が「検証済み」「支出の証明」と表示していた

**対象:** `js/OtherSections.js` の抽出リスト。

**原因:** 一覧は `LBT_gacha.verifyBatch()` を呼び、ハッシュ鎖と開示内容の整合性を確認する。一方、公開鍵署名と外部ビーコンの照合を行う完全な評価は `LBT_gachaIdentity.assessBatch()`／証明画像検証の経路だった。にもかかわらず一覧では一律「検証済み」と表示し、合計を「支出の証明」と表現していたため、署名・外部ビーコンまで真正性が保証されたと誤認させる。

**修正:** 一覧の状態を「ハッシュ鎖OK」「鎖不整合」に変更し、要約・合計に「署名・外部ビーコンは未検証」「合計は記録値」と明記。完全な真正性の確認は「証明画像を検証」で行うよう誘導する。回帰テストで強い誤表示が再導入されないことを確認する。

### 18. 低：部分インポートで未解決の旧チケット移行行が落ちる／壊れた形式の検証が不十分

**対象:** `js/App.js` の `validateImportData`／`IMPORT_GROUPS` と `js/state.js` の旧 `tickets` 移行。

**原因:** 現行状態正規化は、パック名のない旧チケットなど自動移行できない行を捨てずに `tickets` に保持する。部分インポートのカテゴリからこの欄が漏れたり、不正な値形状を事前検証しなかったりすると、バックアップ移行時に未解決情報を失う、または正規化時に不正データを静かに0扱いする可能性がある。

**修正:** 「抽選記録・旧セーブ移行データ」カテゴリに `tickets` を含め、部分ロード許可リストとの一致を維持。インポートでは旧行配列の各要素がオブジェクトであること、または形式別のマップ値が数値／数値文字列であることを確認する。移行不能な種類やパック名なしの値は勝手に加算せず、保持して利用者が後から解決できるようにする。

**追加テスト:** カテゴリ・許可リスト・旧チケット欄の対応と、インポート時の形状検証を回帰テストで固定する。

### 19. 高：特定抽出パックの重複判定が所持ライブラリの保存形式と噛み合わない

**対象:** `js/gacha-tickets.js` の `engineBatchN` と、`js/gacha.js` のテーマパック重複判定。

**原因:** パック抽選へ渡す `heldNames` は `roster.personas[].name` と `roster.egos[].name` から作られていた。しかし所持ライブラリの正準レコードはDB参照型で、通常は名前ではなく人格の `mode/no`、E.G.Oの `rank/no` を保持する。結果として既所持でも名前集合に入らず、同じパック項目を引いた際に `duplicate=false` となり、正規ルールの欠片50付与を逃す可能性があった。

**修正:** 所持レコードに表示名が保存されていない場合は、人格の `mode/no` およびE.G.Oの `rank/no` から `window.DB` を検索し、表示名を引き直して重複判定へ渡す。カスタム名がある場合は、保存された名前を優先する。

**追加テスト:** パック「属せない＆愛することのできない」の「旧G社兵士」を名前フィールドの無い所持レコード（人格No.）として渡し、抽選記録が重複と判定され、欠片50が付与されることを確認する。

### 20. 高：非同期確定待ち中に所持状態が変わると、抽選結果と通帳が不一致になる余地

**対象:** `js/state.js` の `validateDrawBatchApplication`／`applyDrawBatchEffects` と、確定ダイアログを挟む抽選フロー。

**原因:** 確定待ち中の残高・チケット数・二重バッチは再検証していたが、抽選対象がその間に別操作やインポートで所持済みになった場合の再検証が不足していた。所持反映では既存アイテムがスキップされる一方、抽選証明は確定できてしまい、支出明細が抜けたり、チケットだけ消費されたりする可能性があった。テーマパックでは、所持状態の変化により `duplicate` が古くなると欠片50の扱いも合わなくなる。

**修正:** 確定直前に現在の所持ライブラリから人格の `mode/no`、E.G.Oの `rank/no`、表示名を再構築し、各レコードがまだ抽選可能かを順に検査。通常／特異人格やE.G.Oが既に所持済みなら拒否し、テーマパックは実際の所持名と `duplicate` の一致を検査する。これを既存の残高・チケット・費用検証と同じ reducer ガードで再確認し、ズレがあれば取引全体を適用しない。

**追加テスト:** プレビュー後に人格が所持済みになったケースと、テーマパック項目が所持済みへ変わったケースを再現し、取引／チケット／証明が一部適用されないことを確認する。

### 21. 中：インポートの不正な金額・チケット値が0へ正規化され、読み込み成功に見える

**対象:** `js/App.js` の `validateImportData` と `js/state.js` の通帳正規化。

**原因:** 状態側は部分一致の数値解析を避けて不正値を0へ正規化するよう改善済みだが、インポート検証ではネストされた `results[].income / exchange`、`entries[].cost`、各リザルト／明細のチケット数までは数値形式を検証していなかった。そのため、たとえば `"100abc"`、小数や不正な桁区切りが含まれたJSONを読み込むと、ファイル全体は受理されても当該金額が0になり、収支が静かに変わる可能性があった。

**修正:** 通貨・チケットの数量を0以上の安全な整数（正しい3桁区切りを含む）として検証し、値が不正なら `results[0].income.lp` など具体的な項目パスを付けてインポートを拒否する。移行のために意図的に保持する旧 `tickets` 行は、先の専用検証・保留ルールを維持し、現在形式の収入／明細値と混同しない。

**追加テスト:** `100abc`、`2.5`、`tickets.persona="2x"` を拒否し、`1,200` と正しい整数のチケット数は受け入れることを検証する。

### 22. 高：未知・不一致の抽選レコード種別が費用検証を通過する余地

**対象:** `js/state.js` の `validateDrawBatchApplication`。

**原因:** 取引検証はレコードの型と費用を検査するが、`record.kind`・`batch.kind`・`record.item.kind` が同じ抽選ルートを指すか、またアイテムに必要な識別子が含まれるかの契約を完全には検証していなかった。将来のコード回帰や壊れた手動JSONで未知の種別が紛れ込むと、費用は検証されても所持変換関数がその種別を処理せず、結果だけが失われる可能性がある。

**修正:** バッチ種別を人格／E.G.O／テーマパックに限定し、レコード種別を人格／特異人格／E.G.O／テーマパックに限定。各レコードの `item` がオブジェクトであること、定義済みの `item.kind` と `record.kind` が一致すること、人格はNo、E.G.OはNoとランク、テーマパックは名前を持つことを検証する。人格バッチに通常・特異人格が混在するのは許可しつつ、異なるファミリーのレコードを混ぜることは拒否。古い記録で `item.kind` が省略されているケースは後方互換のため受け入れる。

**追加テスト:** 未知の `record.kind`、`item.kind` 不一致、人格とE.G.Oの混在、識別子欠落を用いた取引が、所持・費用・チケットを変える前に拒否されることを追加。

### 23. 中：旧抽出チケット移行で boolean・配列・指数表記を枚数として誤読する可能性

**対象:** `js/state.js` の `legacyTicketCount`／`normalizeStateShape`。

**原因:** 未解決の旧チケット行を保持する仕組みはあったが、移行可能かどうかの判定に `Number.isSafeInteger(Number(ticket.count))` を使っていた。JavaScriptの数値変換では `true` が1、`[2]` が2、`"1e3"` が1000になるため、旧セーブ／JSON内の不正な型や非標準表記が正式なチケット枚数に変わる余地があった。パック名も文字列以外を `String(...)` で暗黙変換しうる形だった。

**修正:** 移行枚数を、数値型の安全な正整数または通常の整数文字列／妥当な3桁区切り文字列だけに限定。boolean、配列、小数、部分一致、指数表記は移行せず、理由コード付きの `_lbtLegacyUnresolved` レコードとして元値を保持。プリミティブ行もオブジェクトに包み、別端末へのJSON移送時に行全体が検証エラーで失われにくい形へ変換。既にラップ済みの未解決行は再ラップせず、再ロードで二重計上しないようにした。

**追加テスト:** 正常な数値／数値文字列は移行し、`true`、`2.5`、`2x`、パック名欠落、`null` は残高に加えず保持し、再ロードでも数・残高が変わらないことを検証する。

### 24. 中：旧ADD_DRAW_BATCH互換経路でチケット抽選の消費を記録していない

**対象:** `js/state.js` の互換用 `ADD_DRAW_BATCH` reducer 分岐。

**原因:** 現行UIは経済効果を `APPLY_DRAW_BATCH`、抽選証明を `ADD_DRAW_RECORD` に分離しているが、旧APIとして残る `ADD_DRAW_BATCH` は `validateDrawBatchApplication` で `ticketSpend` を検査できても、受理後にチケットの消費明細を追加せず、抽選結果の所持反映と証明保存へ進んでいた。旧互換呼び出しでチケット抽選を確定すると、抽選品・証明は保存されるのにチケット残数が減らない可能性がある。

**修正:** 互換分岐でも検証済みの `ticketSpend` を同じ reducer 遷移内で `appendTicketSpend` に渡し、経済効果・証明とともに適用する。決定ログの `entry` も最終の `ADD_DRAW_RECORD` へ渡し、呼び出し側が指定した場合には記録を取りこぼさない。証明のpending keyは `ADD_DRAW_RECORD` が消費するため、永続stateには残らない。

**追加テスト:** 互換APIでチケット1枚を消費したとき、チケット消費明細・所持品・封緘証明・決定ログがそれぞれ一度だけ反映され、残チケットが0になることを追加。

### 25. 高：抽選証明を生成できない場合、証明なしで支払い・所持だけを確定するフォールバック

**対象:** `js/OtherSections.js` の `commitDrawAsync`。

**原因:** `sealBatch` が `null` を返すと、従来のフォールバックは通常バッチの検証を経ずにチケットを消費し、`ADD_ROSTER_MANY` で所持と費用を反映し、`ADD_GACHA_LOG` だけを保存していた。この経路ではハッシュ鎖付きの `draws` 証明が残らず、抽選リストで結果を再検証できないにもかかわらず、利用者には通常の抽選成功として表示される可能性があった。

**修正:** 証明バッチを生成できない場合は、確定を中止して pending を解除し、ページの再読み込みを案内する。チケット消費・通貨支払い・所持追加・決定ログの保存は行わない。証明を生成できた場合だけ、共通の `APPLY_DRAW_BATCH` 検証を通した後に経済取引と `ADD_DRAW_RECORD` を適用する。

**追加テスト:** UIの抽選確定ハンドラーを対象とする契約テストを追加し、`batch` が無い経路では所持追加／チケット消費のフォールバックが存在せず、成功経路は検証済み取引と証明記録を両方 dispatch することを確認する。

1. SHA-256境界、通帳、ローカル日付、部分インポートの入れ子構造、旧チケット移行、抽選Undo/Redoの回帰テストを含め、GitHub Actionsの全通常テストが通ること。失敗時は原因を切り分け、既存テストの検査条件を弱めずに修正する。
2. ローカルのPDF/Python依存を満たした環境で、原典照合・DB来歴監査を実行し、未解決差分を一覧で追跡する。
3. PCとスマートフォンで、新規作成・人格の手動編集・E.G.O解析・所持保存・通帳入力・硝子窓取込・作業状態JSONの部分読み込みを一通り実操作する。
4. ブラウザーをオンライン→オフライン→オンラインへ遷移させ、Service Worker更新失敗時の既存キャッシュ保持、アセット更新後の復帰、共有HTML検索／印刷を確認する。
5. 追加したフィールド整合性契約テストで、INIT_STATE・インポートカテゴリ・APPLY_PARTIAL許可リストの対応を継続検査する。新しい永続フィールドを加えたときは、カテゴリ追加か意図的な除外理由を明記する。

8. 旧保存データに含まれる未解決チケット行（特にパック名なしの旧抽出パック）は自動的に残数へ加算しないが、JSONのバックアップ／部分移送で保持されることを確認し、必要なら利用者が出所を特定できる移行警告UIを追加する。
