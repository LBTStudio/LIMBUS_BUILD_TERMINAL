## 新規発見と今回の修正

### 中：アカウントID衝突で既存保存データを上書きできる

**対象:** `js/state.js` の `newAccountId`、`createAccount`、`migrateLegacyAccounts`。

旧実装はミリ秒タイムスタンプと4桁分の短い `Math.random()` 由来文字列をIDに使い、インデックス上の既存IDと既存保存キーを照合していなかった。IDが衝突すると、新規アカウント本体を `localStorage` へ書いた後に索引を追記するため、既存の `lbt_account_<id>` を上書きしてそのアカウントのキャラクターデータを失う可能性がある。発生確率は通常低いが、影響は保存データの消失に及ぶため防御が必要。

さらに、索引JSONが有効でも同じIDを複数行に持てば、複数のアカウント表示が同じ保存キーを共有し、削除／切替が曖昧になる。従来の `readAccountsIndex()` は重複IDを除去していなかった。

**今回の修正:**
- 16バイトの乱数を利用できるブラウザーではIDのランダム成分を拡張し、再試行回数もIDへ含める。
- 新IDを返す前に、索引内IDと既存の保存キーを両方照合。32回の試行で一意IDを確保できなければ失敗し、既存データへ書き込まない。
- 旧セーブ移行と新規作成の双方でID確保失敗を安全に扱う。
- 読込時に重複した索引IDを一つの保存領域として正規化。
- 既存ID衝突、索引にない孤立保存キーとの衝突、重複索引の回帰テストを追加。

## 横断監査で確認した保証範囲と残存リスク

1. **抽選・経済取引:** #24／#25の検証に、#30の合計費用見積もりが別HEADで追加された。費用表示とエンジン取引の一致は重要だが、#30／#31を同じHEADへ載せた後のCIも必要。抽選公平性は記録整合性と数学的な公平性証明を混同しない。
2. **保存／インポート:** 部分インポートの入れ子型・数量・ID、所持スタック集約、旧チケット保持のテストは存在。旧セーブの実データ全形式を現実のブラウザーで読み書きする検証、および破損データのユーザー向け復旧導線は別に評価する。
3. **共有／外部保存:** トークン長・展開上限・外部保存先のフォールバック回帰はある。外部サービスのCORS・停止・仕様変更はテスト用モックのみでは再現しきれず、共有リンクの完全な公開E2Eは未保証。
4. **DB／原典:** データ構造・本文破損パターン・タグ候補の検査は機械化されている。一方、人格差分候補276件などの原典照合未解決スコープは残り、JSON構造検査を原典一致の証拠に読み替えない。
5. **UI／アクセシビリティ:** 各PRはフォーカス・操作・モバイル条件にソース／契約テストを追加している。ただしPC／Android／iOS実機、スクリーンリーダー、IME入力、印刷、完全オフライン遷移の一通りのE2E実施は確認できていない。
6. **CI／PR統合:** 現行workflowはNode通常テストを実行する一方、`tests/unified-provenance.test.mjs` はPDF/Python依存を理由に通常CIから除外。#30と#31はそれぞれrun #129／#130を通過したが、両方を含む単一HEADでのテスト・生成済み `sw.js` の再同期を別途行う必要がある。両PRは `index.html` と `sw.js` の生成版をそれぞれ更新しているため、マージ後に `node tools/sync-asset-versions.mjs --check` 相当の同期検証を再確認する。

## 結論

今回の追加監査では、上記のアカウントID衝突／重複索引をコード修正と回帰テストへ落とし込んだ。これ以外は、既存CIの成功結果、文書に記載された未完了項目、PR #30／#31の未統合状態を分けて記録した。**全テスト成功は強い自動回帰保証だが、実機E2E・PDF原典との完全照合・抽選の数学的公平性証明まで完了したという意味ではない。**
