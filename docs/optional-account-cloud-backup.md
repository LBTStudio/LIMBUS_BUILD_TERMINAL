# 任意のオンライン保全・復旧

## この機能の前提

オンライン連携は任意です。未連携の利用者は、今まで通り `localStorage` を使ってこのブラウザー内だけで作業できます。初回表示時にデータを自動アップロードせず、アカウントの連携・復旧キーの発行・初回保存は利用者の操作を必要とします。

保全対象は、LBTがアカウントと旧保存データに使う `lbt_*` のうち、アカウント索引・各アカウントの作業状態・アイコン・旧保存の退避キーに限定しています。クラウド認証セッションや復旧キー自体は、バックアップペイロードへ含めません。

### 費用を抑えて運用する

Supabase Freeの枠内で利用する前提ですが、無料枠には容量・稼働条件があり、無料プロジェクトは長期間使われないと一時停止されることがあります。JSONバックアップも別途保管してください。

Googleの基本的なOAuthログイン設定自体は無料で可能です。Google Auth PlatformでWeb OAuthクライアントを作成し、SupabaseのコールバックURLとClient ID / Secretを設定します。LBTでは openid、メールアドレス、プロフィールの基本スコープに限定し、別途有料のGoogle APIは有効化しません。OAuth同意画面・アプリ公開時の要件は別途満たす必要があります。

X APIの利用料金については、X Developer Platformの公式料金案内が従量課金方式を案内し、User: Readを1リソースあたり **US$0.010** と掲載しています。X OAuth2の設定にはDeveloper AppとClient ID / Secretが必要で、ユーザー情報を読み取るAPI呼び出しが課金対象になる可能性があるため、完全無料運用を保証できません。費用ゼロを最優先する間はXを有効化しません。

これはOAuthプロバイダー自体の料金判断です。Supabaseの無料枠、利用上限、プロジェクト一時停止条件は別に適用されます。オンライン保全だけに依存せず、JSONバックアップを別の場所にも保管してください。

公式資料：[Googleログイン設定](https://supabase.com/docs/guides/auth/social-login/auth-google) / [Xログイン設定](https://supabase.com/docs/guides/auth/social-login/auth-twitter) / [X Developer Platformの料金案内](https://developer.x.com/)

## 利用者向けの使い方

### ローカルだけで使う

オンライン保全パネルを無視して、そのままSINNER SELECTでアカウントを選べます。ログインや復旧キーは不要です。

### Google / X連携（未実装）

Google / Xのログイン連携は現在まだ使えません。画面のボタンにも「（未実装）」と表示され、操作できない状態です。オンライン保全を使う場合は「復旧キーを発行して保全」または「全アカウントをJSON保存」を利用してください。

別端末で同じ認証をした場合は、SINNER SELECTのオンライン保全パネルからクラウドデータを復元します。復元前に端末内データがある場合、現在のデータをJSONファイルとしてダウンロードし、確認を取ってから置き換えます。

### 復旧キーを使う

「復旧キーを発行して保全」は、暗号学的乱数で生成したキーを発行し、全アカウントデータをオンラインへ保存します。キーはファイルとしてダウンロードされ、ブラウザーにも自動同期用として保存されます。ファイルを別の安全な場所へ保管してください。

復旧キーは単なる合言葉ではなく、保全データへアクセスできる秘密情報です。Discordや公開チャンネルに貼らないでください。キーを失い、連携したGoogle/Xアカウントも使えず、JSONバックアップも無い場合は復元できません。

### JSONファイルで保全・復元する

「全アカウントをJSON保存」はオンライン認証の有無にかかわらず利用でき、アカウント一覧・各アカウントの状態・アイコンなどをまとめて保存します。「JSONファイルから復元」は保存したファイルを端末に戻します。これはオンラインサービスと独立した退避方法なので、定期的に別の場所へ保存することを推奨します。

## 実装・Supabase設定

このリポジトリのオンライン保全は、既存のSupabaseプロジェクトを利用します。既存の共同セッションテーブルは変更せず、個人アカウント用に専用テーブルを追加します。

1. `supabase/migrations/20261025211015_lbt_account_vaults.sql` を既存プロジェクトに適用します。
2. `supabase/migrations/20261025212903_lbt_account_vault_access_hardening.sql` を適用します。保管庫テーブルの直接アクセスはEdge Function経由に限定するため、ブラウザー向けのRLSポリシーを削除します。テーブル権限も `anon` / `authenticated` には付与せず、サーバー側の `service_role` のみが利用します。
3. `supabase/functions/lbt-account-recovery/index.ts` を `lbt-account-recovery` としてデプロイし、`verify_jwt=false` を指定します。この関数は復旧キーだけでも利用できるため、SupabaseのユーザーJWT検証は自前で行い、復旧キーは256ビットのランダム値をSHA-256でハッシュして検索します。サービスキーはEdge Functionのサーバー環境にのみ置き、ブラウザーには出しません。
4. Supabase Dashboard → Authentication → URL Configurationで、アプリの本番URLと利用する開発用URLをRedirect URLsへ登録します。
5. Google / Xログインを有効にする場合は、それぞれの開発者コンソールでOAuthアプリを作成し、コールバックに `https://hobntjcrzybqsiobrpsz.supabase.co/auth/v1/callback` を設定します。得られたClient ID / SecretはSupabase Dashboard → Authentication → Providersで設定してください。Client Secretをリポジトリやフロントエンドへ追加してはいけません。

Google / Xのプロバイダー認証情報はこのリポジトリには含めていません。Supabase側の設定が未完了の場合、そのログイン方式は利用できませんが、ローカル保存、JSON保全、復旧キー方式を妨げません。 画面のログインボタンはSupabase Authが有効と報告したプロバイダーだけを表示し、無効または状態不明のボタンは隠します。

GoogleとXは別々の認証元です。片方で作成したオンライン保全が、もう片方のログインへ自動的に統合されるとは限りません。継続して使う認証元を一つ決め、別の認証元へ切り替える場合は、先に復旧キーを用意してデータを確認してください。

## 同期と衝突の扱い

- ローカル保存が常に先に行われます。オンライン同期の失敗・オフライン・サービス停止はローカル保存を無効化しません。
- オンライン保全を有効にした後だけ、アカウント保存イベントを受けて遅延同期します。再接続時にも再試行します。
- 別端末からクラウドデータが更新されている場合、古いローカル状態で自動上書きせず同期競合として止めます。
- 更新前のクラウド状態を世代履歴に保存し、直近10世代を復元できます。
- 現在の実装では1スナップショット12MBを上限とします。制限にかかった場合も、端末内JSON保存は利用できます。

- Google/Xだけで使う構成も可能です。復旧キーを発行した場合は、Google/Xに加えてキーからも復元できるようになります。初回にローカルデータを自動送信することはありません。
- 既に保全データがあるOAuthアカウントでは、復旧キー発行時にクラウドの内容を維持したままキーだけを結びつけます。ローカルとクラウドが異なる場合は自動同期を停止し、どちらを使うか選ぶ必要があります。
- ブラウザーの保存領域を消してGoogle/Xで再ログインした場合、クラウドに登録済みの復旧キーは「復旧キーを再発行」から更新できます。再発行すると旧キーは無効になります。
- 復旧キーだけで新しいオンライン保管庫を作成できる操作には、接続元ごとに1時間あたり10回の作成制限を設けています。既存の保管庫への正しいキーによるアクセスは別扱いです。
- Google/Xアカウントの削除時、復旧キーが登録されている保管庫はユーザーIDとの結びつきを外して残します。復旧キーの無いOAuth専用保管庫は、復元手段が残らないためAuthユーザーとともに削除されます。

- 無料サービスは停止・一時停止・仕様変更・障害の可能性があります。オンライン保全だけを唯一の退避先にせず、JSONを別の保管場所にも保存してください。
