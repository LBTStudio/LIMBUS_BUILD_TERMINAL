# 長文キャラクターシート共有方式 — 目的起点の三専門視点レビュー

**対象:** LIMBUS BUILD TERMINAL（LBT）  
**作成日:** 2026-08-17  
**目的:** 1万文字級になり得るキャラクターデータを、発行者・閲覧者にログイン、登録、CAPTCHA、手動保存、期限管理を求めず、Discordで短いリンクとして共有し、少なくとも1〜3日、可能なら長期に閲覧可能にする。運営者への自動請求は絶対に発生させない。

## 1. 問題の再定義

これは「URLをもっと圧縮する」問題ではない。必要なのは、**長文の状態データを安全に保持し、短い参照だけをDiscordへ渡し、閲覧時に整形済みシートへ復元する共有プロトコル**である。

任意の1万文字データを、情報を失わず常に2,000文字未満の単独URLへ変換する可逆変換は存在しない。これは圧縮アルゴリズムの不足ではなく、入力集合の方が出力集合より大きくなる情報量の制約である。したがって、一定量を超えるデータには必ず**参照先（短縮表または共有ストア）**が必要になる。

> 重要なのは、データ本体をどこかへ置くことではなく、**利用者にその保管先を意識させず、請求を発生させず、リンクの読み手に安全なHTMLを返すこと**である。

## 2. 専門家A — 配信基盤設計者

### 主張

「共有の土台」は、データ保存とHTML配信を分離すべきである。生HTMLを匿名アップローダーへ丸ごと送る方式は、保存期限、CORS、OGP、規約、障害時の再発行をサービスごとに抱え込む。代わりに、LBTが生成した**構造化状態データ**を保存し、閲覧ページは固定の安全なテンプレートとして配信する。

閲覧用エンドポイントは、保存済みデータをそのまま実行可能HTMLとして返さない。`/s/<短いID>`は人格名・同期状態・概要をOGPとして含む最小HTMLを返し、同ページ内のLBT共有ビューアがJSONを取得してシートを描画する。この構造ならDiscordはサーバー応答だけでカードを取得でき、閲覧者にはLBTと同じ整形済みシートを出せる。

### 配信方式の比較

| 方式 | 1万文字を短URL化 | Discordカード | 利用者操作 | 継続性 | 評価 |
| --- | --- | --- | --- | --- | --- |
| URL内データのみ | 不可 | 静的のみ | なし | GitHub Pages依存 | 短文用として残す |
| 匿名HTMLアップローダー | 可能 | サービス次第 | なし | 各サービスの保持規約 | 単独採用は不安定 |
| URL短縮器 + URL内データ | 5,000文字程度まで | リダイレクト先次第 | なし | 短縮器依存 | 中量データに有効 |
| 中央の無償共有API | 可能 | 可能 | なし | 上限まで明示制御可能 | 長文の本命 |
| 利用者所有Gist等 | 可能 | 可能 | 発行者ログインが必要 | 所有者依存 | 要件外 |
| IPFS/Nostr等 | 可能 | 不安定 | 通常は利用者に負担 | ピン／Relay方針依存 | 要件外 |

Cloudflare Workers Freeは1日100,000リクエストまでで、超過時はエラー1027を返す。[1] D1 Freeも日次上限超過時はエラーを返し、継続利用には明示的なWorkers Paidへのアップグレードが必要である。[2] すなわち、**Paidを有効化しなければ無料枠を越えて自動請求される設計ではない**。FreeのD1保存上限は5 GBである。[3]

### 結論

長文の本命は、固定の共有ビューアと短縮IDを返す無償中央APIである。期限は初期値を30日とし、保存行の`expires_at`で即時に非公開化する。物理削除は発行・閲覧リクエスト中に少量ずつ行えば、Cronや常時稼働は不要になる。恒久リンクも用意できるが、保存領域が80%に達した時点で**新規の恒久発行だけ停止**し、既存リンクの閲覧を優先する。

## 3. 専門家B — 情報符号化・共有プロトコル設計者

### 主張

共有するべきものは生成済みHTMLではなく、**バージョン付きの構造化シート状態**である。HTMLを保存すると、古いCSS・レイアウト・危険な文字列をそのまま抱え込み、LBTの表示更新を反映できない。一方で状態を保存すれば、LBTの固定ビューアが常に同じルールで描画し、人格名や同期MAX、スキル、E.G.O、所持品、オリジナルデータ、改行、`-`、`「`、`/`などを完全に復元できる。

提案する共有パッケージは以下である。

```text
ShareEnvelope v1
├─ metadata: title / personaLabel / thumbnail description / schema version
├─ payload: 完全なビルド状態（JSON）
├─ checksum: SHA-256(payload)
└─ rendering: viewer version
```

`metadata`はWorkerがカードHTMLを作るための最小フィールドで、`payload`はLBT共有ビューアが復元する唯一の正本である。既存DBと一致する人格・E.G.O・アイテムは参照IDとして圧縮し、オリジナル人格・オリジナルアイテム・編集済み効果文は内容を省略せず`payload`へそのまま残す。

### 型破りだが有効な二層短縮

中央APIを全発行に使う必要はない。共有発行を以下の**段階的トランスポート**にする。

| 層 | 対象 | 出力URL | 保存されるもの | 目的 |
| --- | --- | --- | --- | --- |
| 0 | 小さい状態 | GitHub Pages共有URL | なし | 最速・完全オフライン |
| 1 | 中程度の状態 | URL短縮器のURL | 短縮器内の遷移先 | Discord 2,000文字回避 |
| 2 | 5,000文字超の長文 | LBT共有ID URL | 構造化状態 | 1万文字以上の完全保持 |

is.gdは匿名のHTTPS API、通常約19文字の短縮URL、恒久的な301リダイレクトを提供する。`#`、`;`、`+`、`&`などを含む遷移先はURLエンコードで扱える。[4] ただし遷移先URLは5,000文字までで、レート制限と無効化条件がある。[5] [6] よって短縮器は**共有ストアの代替ではなく、自己完結URLをDiscordへ渡すための軽量トランスポート層**として使う。

TinyURLの旧匿名APIは12,000文字のテストURLを短縮できたが、実ブラウザでは中間プレビューへ遷移した。Discordが中間ページのOGPを取得する可能性があるため、主経路には採用しない。

### 結論

データ形式を一つに固定し、配送だけを三層化する。これにより、通常は外部保存なし、長文だけは短縮ID保存、さらに中間領域ではURL短縮器という最小コストの経路を取れる。

## 4. 専門家C — 共有体験・安全性設計者

### 主張

利用者にログイン、CAPTCHA、アカウント、期限選択、アップロード先選択を見せてはならない。共有ボタンは一つにし、内部で最適な配送層を決めるべきである。

ただし「利用者に制約を出さない」と「公開書込みを無制限に許す」は同義ではない。無制限の匿名アップロードは、どの無料サービスでも乱用や停止を招く。制約は利用者の画面ではなく**サービス側の資源制御**として持つ。

### 利用者に見せない安全装置

| 制御 | 利用者への影響 | 目的 |
| --- | --- | --- |
| 256 KiB以下の構造化状態上限 | 通常の1万文字級シートには影響なし | 巨大データ・不正利用の抑止 |
| 形式検証とHTMLエスケープ | 操作不要 | XSSや任意スクリプト保存の防止 |
| サーバー側の発行頻度制御 | 通常は不可視 | 連続自動投稿の抑止 |
| ハッシュ計算量証明（必要時のみ） | ボタン押下後の短い処理待ちのみ | CAPTCHAなしの機械的乱用抑止 |
| 期限切れの即時非公開化 | 操作不要 | 容量の自動回収 |
| Free上限到達時の明示エラー | 追加請求なし | 請求ゼロの保証 |

計算量証明は、クライアントが短いNonce探索を行い、WorkerがSHA-256結果を検証する方式である。ユーザーに問題を解かせず、CAPTCHAも表示せず、ボットの大量発行コストだけを上げる。端末性能が低い場合は難易度を下げるか、短縮器・自己完結URLを優先して待機を避ける。

Rentryは匿名API、ランダムURL、編集コード、共有用メタデータを持つため、**テキスト版の予備出力**には使える。[7] しかしMarkdown主体であり、LBTのHTML/CSSを完全に実行・再現するわけではない。PrivateBinは暗号化されたペーストで、復号鍵がURL fragmentにあるためDiscordクローラーが共有内容を読めない。[8] これらを主要経路にすると、共有品質のばらつきが利用者に露出する。

### 結論

配信先の選択を利用者に委ねず、「Discord共有」を一回の操作にする。利用者に見せる結果はURL、コピー成功、保持期限だけでよい。外部サービスの障害・レート制限は内部で経路変更または明快な失敗理由として扱う。

## 5. 相互反論

| 論点 | 配信基盤設計者 | 情報符号化設計者 | 共有体験・安全性設計者 | 結論 |
| --- | --- | --- | --- | --- |
| 公開アップローダーを分散採用すべきか | 単独依存よりは強いが、サービス差をLBTが吸収できない | HTML自体より状態を持つべき | 障害時に利用者へ選択を迫る | **主経路にはしない**。予備のテキスト出力に限定 |
| URL短縮器だけで解決するか | 速いが保持は他社依存 | 5,000文字上限がある | 一回操作で扱える | **中量データの第2層**として採用 |
| 中央APIは利用者無制約に反するか | 運営者の一回設定だけでよい | 長文の参照先に必須 | 利用者の画面には現れない | **長文の第3層**として採用 |
| すべてを恒久保存するか | 5 GBで上限がある | 正本は保持できる | 不要データが蓄積し、将来の停止を招く | 初期30日、恒久は容量保護付き |
| CAPTCHAなしで公開書込みを守れるか | 資源上限で最終停止 | 計算量証明が使える | UI摩擦を出さない | サーバー側制御を重ねる |

## 6. 統合提案: 「LBT Share Fabric」

三者の結論は、**一つの外部サービスを選ぶことではなく、状態と配送を分離した三層共有ファブリックを作ること**で一致した。

```mermaid
flowchart LR
  A[共有ボタン] --> B[完全な構造化状態を作成]
  B --> C{URL長}
  C -->|小さい| D[GitHub Pages自己完結URL]
  C -->|5,000文字以内| E[is.gd短縮URL]
  C -->|長文| F[Free D1共有API]
  F --> G[/s/短いID + 動的OGP]
  D --> H[共有ビューア]
  E --> H
  G --> H
  H --> I[完全なキャラクターシート]
```

### この案が目的に最も近い理由

| 要求 | 実現方法 |
| --- | --- |
| 1万文字級の完全保持 | 長文はURLでなく状態ストアへ保存 |
| 短いDiscordリンク | is.gdまたは短縮IDを返す |
| 人格名入りDiscordカード | 長文用Workerが動的OGPを返す |
| 利用者無制約 | ログイン、CAPTCHA、保存先選択、期限選択をUIに出さない |
| 請求ゼロ | Workers/D1 Freeのみを使い、Paidを有効化しない。上限では停止 |
| 最低1〜3日保持 | 初期30日TTL。期限後は即時非公開 |
| 理想的な恒久性 | 容量余裕内で永続行を保持。ただしFreeサービスに無条件の永久保証はない |
| 外部サービス障害の耐性 | URL内共有、短縮器、中央APIが独立して機能する |

## 7. 実装時の非交渉条件

1. ユーザー入力を含むHTMLを、共有ドメインでそのまま実行しない。保存するのは構造化JSONであり、ビューアは既存のエスケープ規則で描画する。
2. CloudflareアカウントにはPaidプラン、R2、課金アカウント、支払い情報を紐付けない。Free上限到達時はエラーにして、新規共有を停止する。
3. 短縮器は規約に従う。一つのサービスを大量生成器として扱わず、共有ボタンの明示操作時だけ呼び出し、応答を再利用する。
4. Discordの外部クローラーがJavaScriptを実行しない前提で、カード用メタデータはHTTPレスポンスの`<head>`へサーバー側で入れる。
5. 期限と公開性を共有モーダルへ明示する。公開リンクを知る者は内容を読めるため、秘匿データ用ではない。

## 8. 次の実装判断

実装を開始するなら、まず共有パッケージ（構造化JSON＋メタデータ）の形式を固定し、現在の自己完結共有を層0として残す。次に、is.gdを層1の「Discord短縮」へ試験導入する。最後に、Cloudflare Free + D1を長文の層2として接続する。この順序なら、外部サービスの導入に失敗しても既存共有を壊さず、利用者には常に一つの共有操作だけを提供できる。
