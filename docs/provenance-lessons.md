# 出典照合で得た教訓と注意点

原典PDFとDB、そしてCCFOLIA出力の三段階を監査する作業で、実際に詰まった場所と
判断の根拠を残す。同じ型の問題に次に当たったとき、調査をやり直さずに済むようにする。

対象の道具は `tools/provenance/`、目標と方針は
[docs/output-fidelity-goal.md](output-fidelity-goal.md) にある。

---

## 1. 最大の教訓 —「監査0件」は何も保証しない

この作業は、利用者から「戦術4の `敵討伐時` が改行されない」と報告されて始まった。
報告を受けた時点で、先行作業の完了条件は**すべて満たされていた**。

```
node tools/provenance/audit-output-lossless.mjs  → 検出: 0件
node tools/provenance/audit-db-text.mjs          → 要修正: 0件
node --test "tests/*.test.mjs"                   → 206件すべて成功
```

破損が現に起きているのに、監査は0件を返し続けていた。

### なぜ見逃したか

監査が検査していたのは `splitEffectLinesPlain()` という内部関数だった。
一方で利用者が受け取るのは `buildPalette()` などの出力である。
そしてダイス効果は、この内部関数を**一度も通っていなかった**。

```
監査が見ていた経路 : DB本文 → splitEffectLinesPlain() → 検査
実際の出力の経路   : DB本文 → sanitizeInline()（改行を空白へ）→ 連結 → 利用者
```

分割器をいくら精密に検査しても、分割器を使わない経路の欠陥は永久に出てこない。
監査は「正しく動いている」のではなく、「何も見ていなかった」。

### 対処

監査の対象を、内部関数から実際の出力（4経路）へ移した。
そのうえで、**検出すべき破損を注入したら必ず検出すること**をテストにした
（`tests/audit-non-vacuity.test.mjs`）。

先行作業もこの確認を人手で一度は行っている。しかしテストではなかったため、
出力経路が増えたときに監査が追随しているかを誰も検証できなかった。
注入試験をテストに落とすことで、「監査対象と出力経路の乖離」自体を検出対象にした。

> **注意点**: 新しい出力経路を追加したら、`OUTPUT_ROUTES`（`output-paragraphs.mjs`）へ
> 必ず追加する。追加を忘れると、その経路は監査の外に置かれる。
> 非空虚性テストは `OUTPUT_ROUTES` を回すので、登録さえすれば注入試験も自動で増える。

### 派生する注意点 — 正規化のしすぎで監査が盲目になる

段階1の照合関数 `canon()` は、比較前に空白と改行をすべて落とす。

```js
const NOISE_RE = /[\s\u3000。、，,．.・：:；;／/]/g;
```

PDFの組版由来の差を吸収するための設計で、文字の混入・欠落には有効である。
しかし改行が比較に影響しないため、「原典が2段落で書いた本文をDBが1段落へ連結している」
という型は**定義上検出できない**。実際にこの型の破損が63件あった。

正規化は「何を同一とみなすか」の宣言であり、そこで落とした情報は
その監査では永久に見えない。監査を足すときは、既存の正規化が
何を見えなくしているかを先に確かめる。

## 2. 段落境界の判定 — 推測せず組版情報を使う

PDFから抽出したテキストの改行は、二つが混ざっていて区別できない。

- **折り返し** — 一つの段落が組版上の桁数で折り返されただけ
- **段落境界** — 原典が意図して改行した位置

「句点で終わっていたら段落」のようなヒューリスティックは使わなかった。
原典には句点で終わらない段落も、段落の途中に句点がある本文も両方ある。

採用した基準は「**行末の余白に、次の行の先頭文字が入ったか**」である。
入らなかったのなら改行は組版の都合であり、入るのに改行したなら原典の意思である。

```
紙面206「N社握らんとする者」戦術4
  自分に狂信があるならダメージ量+5。対象が機械融和生命体なら追  余白 0.0pt → 折り返し
  30-6d5：的中時、対象の出血が5以上なら火傷7を付与。           余白27.5pt → 段落境界
  敵討伐時、次のRに打撃威力増加1を得る
```

この基準を実装するまでに、次の四つで順に詰まった。すべて実装済みだが、
コーパス抽出器（`extract_pdf_corpus.py`）を触るときの注意点として残す。

### 落とし穴A — 頁をy座標順に並べると行見出しが本文へ割り込む

人格データの紙面は表組みで、左端に `固` `有` `戦` `術` といった行見出しの列がある。
これらは本文と高さが重なるため、頁全体を y 順に並べると折り返しの間へ入り込む。

```
誤: R終了時、次のRにデュラハン1を得る。自分が士気低下状態または混乱状
    固                                    ← 行見出しが割り込む
    態なら消滅
```

**対処**: 行を字下げ位置（x0）ごとのセルへまとめてから、セル単位で読み順に並べる。
紙面の隅のノンブル（頁番号）が本文末尾へ混入する問題も同時に解消する。

### 落とし穴B — 段の右端をセル内の最大値で推定すると誤る

セルの最長行がたまたま段落の終わりだった場合、その行の余白が0になり、
段落境界を折り返しと誤判定する。

```
紙面205「N社握らんとする者」スキル2
  マッチ開始時：対象が機械融和生命体ならスキル威力+2  x1=223.56 ← セル内の最大
  マッチ勝利時：次のRに狂信2を得る                   x1=170.01
```

セル内最大（223.56）を右端とすると1行目の余白が0となり、二つの段落が連結されてしまう。

**対処**: 段の右端は、文書全体で同じ字下げ位置に現れる行の x1 の最大値から求める
（`ColumnEdges`）。折り返しは文書全体で何度も起きるので、
どこかの行が必ず本当の右端まで到達している。

なお、紙面単位の最大値も使えない。能力値行など本文より幅広に組まれた行が
同じ紙面にあり、右端を引き伸ばしてしまう。

### 落とし穴C — 行頭禁則を考慮しないと余白の比較が成り立たない

日本語の組版では句読点や閉じ括弧を行頭に置けない。禁則が働いた行は、
余白が1文字分あっても、実際には2文字分の空きがないと前の行へ送れない。

```
紙面97「北部ヂェーヴィチ協会4課フィクサー」
  舞台開始時、デリバリーキャリアが0の状態で開始す  余白7.10pt
  る。戦線離脱時、ランダムな味方2名にマッチ威力増加
```

余白7.10ptは全角1文字（6.00pt）より広いので、単純な比較では段落境界に見える。
しかし次の行は「る。」で始まり、「。」を行頭へ置けないため「る」も送れなかった。
必要なのは2文字分（12.00pt）で、余白は足りていない。

**対処**: 次の行の先頭に続く行頭禁則文字の幅を合算して比べる。

> **注意点**: 禁則文字に小書き仮名（`ッ` `ャ` など）や長音符を含めてはいけない。
> これらも本来は行頭禁則だが、語の途中にも現れるため過大に数えてしまう。
>
> ```
> マッチ敗北時：次のRにパワー2を得る
>  ^ 「ッ」は語中の促音であって、行頭へ送られた文字ではない
> ```
>
> これを数えると必要幅を2文字分と見積もり、実際には段落境界である位置を
> 折り返しと誤る。対象は句読点と閉じ括弧に限る。

### 落とし穴D — 判定できない位置がある。そこは報告しない

余白が1文字に満たない位置では、折り返しと段落境界を組版から区別できない。

```
紙面119「黒獣-巳」スキル2
  使用時：自分の呼吸と対象の破裂の合計が10以上ならスキルd値+1  余白3.36pt
  マッチ勝利時：呼吸4を得て対象に破裂3を付与
```

抽出器は折り返しとして連結するが、続く行は発動タイミング見出しで始まっており、
原典が改段したと読むのが自然である。組版からは一意に定まらない。

**対処**: この位置は判定せず、報告もしない。
偽陽性を出すと、監査の指摘が信用されなくなり、
本当の破損が埋もれる。判定できないことを認めるほうが安全である。

## 3. 修復の進め方 — 文字は変えず、改行だけを戻す

DBの修復63件は、すべて「原典が改段している位置へ改行を戻す」または
「原典に無い改行を取り除く」だけで、文字は一切変えていない。
ルールの解釈に踏み込む書き換えはしない（`docs/output-fidelity-goal.md` の非目標）。

修復は `tools/provenance/repairs.json` へ出典・理由つきで記録し、
`apply-repairs.mjs` が適用する。`before` が現在のDB本文と一致しなければ適用を中止するので、
表が古い場合や二重適用に気づける。

> **注意点**: `before` には**項目の値全体**を入れる。該当する1行だけを入れると、
> 同じ項目が他の行も持っている場合に一致せず、適用が止まる。
> `db-paragraphs.mjs` は `fieldBefore` / `fieldAfter` として
> 項目全体の現在値と修復後の値を返すので、これを使う。

修復案は手で書かず、監査の指摘から機械的に生成する（`plan-paragraph-repairs.mjs`）。
63件を手で書き写すと転記の誤りが入り、それは原典との照合では検出できない
（DBが原典と一致しなくなるだけなので検出はされるが、原因の切り分けに時間がかかる）。

## 4. 照合の精度 — 文脈の長さで誤った項目を指してしまう

出力の照合は、段落境界の前後の本文を出力の中から探す形で行う。
このとき切り出す文脈が短いと、同じ人格の別のスキルへ誤って一致する。

```
スキル3 …ダメージ量+1（最大10） 自分のデリバリーキャリア10ごとにスキルd数+1
スキル4 …ダメージ量+1（最大10）⏎自分のデリバリーキャリア10ごとにスキルd値+1。
```

12文字では両者の前後が同じになり、スキル3の欠落をスキル4の指摘として報告した。
指摘された項目を調べても出力は正しいので、原因にたどり着けない。

**対処**: 文脈を24文字まで取る（`CONTEXT_LENGTH`）。
段落が短ければその全体を使い、長い場合だけ上限で切る。

### 関連 — 区切り記号を正規化で消さない

照合の前に体裁の差を取り除くが、段落の先頭に付く `▶︎` や `<br>` は
**区切りそのもの**なので消してはいけない。

```
出力     …（最大10）\n▶︎自分のデリバリー…   ← 正しく区切られている
▶︎を除去  …（最大10）\n自分のデリバリー…
\nも除去  …（最大10）自分のデリバリー…      ← 誤検出
```

除去してよいのは、意味を持たない空白と字下げだけである。

## 5. 段落分割器を触るときの注意 — `\d+R` は見出しとは限らない

`\d+R` はラウンド進行の見出し（`1R：全ての味方が…`）として現れるが、
それ以外の用法も多い。

| 用法 | 例 | 段落境界か |
|---|---|---|
| ラウンド進行の見出し | `1R：全ての味方がクイック1を得る` | はい |
| 状態表記 | `[1R] 虚弱の数だけ攻撃スキル威力減少` | いいえ |
| 回数制限 | `視線1を付与（1Rに2回）` | いいえ |
| 持続期間 | `自分に怠惰保護2を3Rの間付与する` | いいえ |
| 開始時期 | `このパッシブを得てから3Rの間…` | いいえ |

状態表記と回数制限は括弧の内側にあるので括弧の深さで除ける。
しかし持続期間と開始時期は文中に素で現れ、括弧では区別できない。

原典の全段落を数えると、`\d+R` が段落の先頭に立つのは47件中44件が `\d+R：` の形で、
括弧外で見出しになるのは3件だけだった。一方 `Rの間` `R以降` のような持続表記は
段落の途中に現れる。この分布を根拠に、**区切り記号 `：` を伴う場合だけ**を
見出しとして扱うことにした。これで14件の誤分割が解消した。

> **注意点**: 分割器の条件を緩めると、原典が一文で書いた本文を切ってしまう。
> 変更したら `tests/output-paragraphs.test.mjs` の持続表記の試験を必ず通す。

## 6. 作業を再現するための手順

```bash
# 原典PDFからコーパスを作り直す（sources/ のPDFを使う。引数は不要）
python3 tools/provenance/extract_pdf_corpus.py

# 四つの監査。いずれも0件で通る状態を維持する
node tools/provenance/audit-db-text.mjs            # 段階1: 文字が原典に実在するか
node tools/provenance/audit-db-paragraphs.mjs      # 段階1: 段落構造が原典と一致するか
node tools/provenance/audit-output-lossless.mjs    # 段階3: 分割器が本文を壊さないか
node tools/provenance/audit-output-paragraphs.mjs  # 段階3: 実出力が段落を保つか

# 段落の破損が見つかった場合、修復案を作って適用する
node tools/provenance/plan-paragraph-repairs.mjs           # 案を確認
node tools/provenance/plan-paragraph-repairs.mjs --write   # repairs.json へ追記
node tools/provenance/apply-repairs.mjs                    # 適用内容を確認
node tools/provenance/apply-repairs.mjs --write            # data/db.json を更新

# 回帰テスト（監査の非空虚性を含む）
node --test "tests/*.test.mjs"
```

原典PDFは `sources/` に置いてある。以前はPDFが手元にある場合しかコーパスを
作り直せなかったが、リポジトリ内で完結するようにした。

## 7. 判断に迷ったときの指針

この作業で繰り返し立ち返った基準を三つ挙げる。

1. **原典が唯一の根拠である。** DBは原典の転記物であり、
   原典に無い本文はDBに存在してはならない。ルールの解釈や調整はしない。

2. **判定できないことを認める。** 組版から一意に定まらない位置では報告しない。
   偽陽性は監査への信頼を損ない、本当の破損を埋もれさせる。
   疑わしきは「判定不能」として別に置く。

3. **監査が働いていることを、監査自身で示す。** 0件という表示は、
   検出すべきものを検出できると示して初めて意味を持つ。
   人手で一度確認するだけでは、経路が増えたときに静かに空虚化する。
