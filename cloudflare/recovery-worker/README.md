# Cloud backup, stable recovery key, and failover

LBT's recovery key is immutable. It is generated once and must not be rotated or regenerated by an update, restore, provider switch, or account revision. Losing the key can make every remote copy unrecoverable, so store the key offline and separately from the browser.

## Provider model

- Supabase is the primary provider.
- Cloudflare D1 is an independent fallback provider. Its Worker must not call Supabase.
- On a normal successful write, LBT attempts a revision-checked copy to the other provider.
- When Supabase is unreachable or returns a retryable service error, reads and writes can use Cloudflare. A 4xx key/validation error is not treated as an outage.
- On read, the app compares provider revisions. A newer revision may be copied to the older provider only when the target's expected revision still matches. If providers have different payloads at the same revision, automatic repair stops and surfaces a conflict.
- When Supabase recovers, the next successful dual-read reconciles the newer provider to the older provider before normal operation continues.
- Provider writes are best-effort replicated, not a distributed atomic transaction. The UI must never claim dual protection unless both writes or a repair have succeeded. Keep an independent JSON backup as well.

## Cloudflare D1 Worker

The independent worker lives in cloudflare/recovery-worker and exposes:

- GET /healthz — provider health/configuration.
- POST /api/v1/recovery — recovery API.
- GET /api/stats/view?path=app|share|view — increments and returns the page-view counter.

### Setup

1. Verify that the Cloudflare account stays on a zero-cost Workers Free plan. The connected API cannot always read account billing status; do not upgrade or enable paid products to complete this setup.
2. Create a D1 database named lbt-recovery in the same account.
3. Apply schema.sql to that database.
4. Replace REPLACE_WITH_D1_DATABASE_ID in wrangler.toml with the actual D1 ID.
5. Deploy worker.js as a new Worker named lbt-recovery. Do not overwrite the existing lbt-ogp Worker.
6. Open /healthz; it must return an ok response for provider cloudflare-d1 with configured true.
7. Test create, update, get, history, restore, replica sync, and the access counter with non-production test data before enabling Cloudflare failover for real users.

The Worker stores SHA-256 hashes of recovery keys, never the plaintext recovery key. The current payload format is stored as JSON, as with the existing Supabase API; this design does not provide end-to-end encryption against the storage providers. Do not store passwords, OAuth tokens, or unrelated sensitive personal data in these snapshots.

## Limits and reliability

The Worker splits payloads into small D1 rows because D1 rows are limited to about 2 MB. The configured payload limit remains 12 MiB and history is capped at 10 generations per key. D1 Free allows 500 MB per database and 5 GB across an account, with daily read/write limits. These shared account limits mean no unconditional capacity guarantee is possible; the app must show sync errors and retain local/JSON backups if the cap is reached.

The page counter records aggregate page views; it does not attempt to count unique visitors and does not store IP addresses in the database. Public counters can be inflated by bots or abuse and are informational, not billing-grade analytics.

## Current communication model

With both providers enabled, one page initialization reads the recovery vault from both providers to detect divergence (up to 2 HTTP requests). A changed snapshot then produces one primary write plus one best-effort mirror write. Recovery/history operations may query both providers. This favors recoverability over minimal request count. The feature is optional; with no recovery key, no recovery-provider traffic is sent. The separate access counter performs one request per page load.

Do not mark the product fully failover-ready until the Cloudflare Worker is actually deployed and the multi-provider tests pass. The fallback URL in js/cloud-backup.js must match the deployed Worker hostname.
